Three long-context classifiers that cover most of finance NLP

Aspect sentiment, forward-looking detection, and fact versus opinion. Three small encoders that read a whole passage, not one sentence. One domain, one shared evaluation protocol. This document fixes what gets built, what the labels mean, and what counts as done. It is the build spec, not a pitch.

Why these three

The thesis

Claim under test

Most useful questions about a piece of financial text reduce to three smaller questions. Who or what is this about, and is it good or bad for them. Is this about the past or the future. Is this something checkable, or is it somebody's view. Answer all three and you can filter, route, score and summarise almost any financial document.

Aspect sentiment

Sentiment is useless without a target. A sentence can be good for the supplier and bad for the buyer. Tying polarity to a named aspect is what makes the signal usable.

Forward-looking

Guidance moves prices. Reported history is already in the tape. Separating the two is the single cheapest way to raise the value of any downstream sentiment score.

Fact vs opinion

A number in a filing and an analyst's judgement are not the same evidence. Anything that summarises or ranks financial text needs to know which one it is holding.

The three combine. Run all three over the same sentence and you get a structured record: target, polarity, time direction, evidence type. That record is the real product. The models are just the way to get it cheaply.

And all three need the passage, not the sentence. A person answering any of these three questions reads around the sentence first. So does an LLM. A 512-token encoder cannot, and that is the main reason small encoders lose the cases that matter. These models read up to 8,192 tokens, which is the same evidence the LLM baseline gets. The comparison is then about the model, not about who was allowed to read more.

The thesis is a claim, not a given. It is not proven by building the models. It gets tested in the write-up by taking real finance NLP tasks and showing what the three outputs do and do not cover. Coverage gaps get listed honestly. See the write-up plan.

Exact input and output

Model contracts

Decided

Three separate fine-tuned encoders. Same base model, same input format, same evaluation harness. Each is released on its own and versioned on its own. All three take a passage and a target span inside it, and all three read up to 8,192 tokens.

Aspect-based sentiment

modernfin-absa

3-class
Input
(target_sentence, passage, aspect). The aspect is supplied by the caller. The model does not find it.
Output
positive | negative | neutral, with a probability for each.
Question it answers
Given this text, is the sentiment expressed toward this specific aspect good, bad, or neither?
Aspect can be
A company, a ticker, a business segment, a product, or a financial metric such as gross margin.
Primary metric
Macro-F1 across the three classes.

Aspect extraction is out of scope. If nobody hands you an aspect, this model has nothing to do. A separate extractor can be built later, and it is not part of this project.

Forward-looking statement detection

modernfin-fls

Binary
Input
(target_sentence, passage). No aspect.
Output
forward_looking | not_forward_looking, with a probability.
Question it answers
Does this sentence make a claim about a future state of the world?
Primary metric
Macro-F1. Positive-class F1 and recall reported alongside, because the positive class is the rare and useful one.

Fact versus opinion

modernfin-factop

Binary
Input
(target_sentence, passage). No aspect.
Output
fact | opinion, with a probability.
Question it answers
Could a reader check this against a source, or is it somebody's judgement?
Primary metric
Macro-F1.

No "mixed" class, on purpose. Sentences that state a number and then judge it are common. The codebook forces them into one bucket by a written rule. A third class was rejected because annotator agreement drops and the label stops being useful downstream.

Shared input format

All three models take a passage and a character span inside it. The caller hands over as much of the document as it has. The model decides how much of it to read.

{
  "passage":      "... Margins compressed 180bps year over year. We expect gross margin
                   to improve modestly in the second half. Pricing actions take effect in Q3 ...",
  "target_span":  [46, 118],       // character offsets of the sentence being classified
  "aspect":       "gross margin"   // modernfin-absa only
}

The passage may be a paragraph, an MD&A section, a full answer in a question-and-answer exchange, or a short filing item. The target span is never truncated. Everything else is trimmed to fit the length budget by the rules in Architecture → Input construction. A convenience wrapper still accepts the old (target, context_before, context_after) form and builds the passage for you.

The change that makes this competitive

Why long context

Decided

The previous version of this plan capped the input at 512 tokens. That cap is removed. The ceiling is now 8,192 tokens, which is what the base encoder natively supports. This is the single biggest change in the spec and it needs a stated reason, because a long-context attempt failed once already.

The argument for it

  • It is the honest comparison. An LLM baseline is handed the whole passage. Handing the encoder two neighbouring sentences and then calling the result a fair fight is not a fair fight.
  • Finance evidence is far apart. The number is in a table at the top of the section. The judgement about it is three paragraphs down. Both are needed and they are rarely adjacent.
  • Attribution needs the speaker. "Margins will improve" is opinion or fact depending on who is talking, and in a transcript the speaker tag can be hundreds of tokens back.
  • It is free capability. ModernBERT was pretrained at 8,192 tokens. Capping it at 512 throws away something already paid for.
  • Cost still wins by a wide margin. A 150M encoder over 8,192 tokens is still orders of magnitude cheaper than a frontier model over the same text.

What went wrong last time

  • The long run trained on rows that were still 52.8% truncated at 6,144 tokens. The examples were malformed before length was ever the issue.
  • A later attempt measured 78.2% truncation at 4,096 and an assertion correctly stopped the run.
  • Provenance on the long data could not be reconstructed afterwards.
  • So the finding was "the long data was broken", not "length does not help". Those are different results and only the first one was actually measured.

Full record in prior learnings.

The truncation gate

No long-context training run starts until the truncation rate at the configured length is measured and recorded. Above 5% of rows losing any target-adjacent content, the run is blocked and the data builder is fixed first. This is the direct countermeasure for the previous failure, and it is enforced by an assertion, not by care.

Length is a measured choice, not a slogan

LengthRoleWhat it settles
512 The control. What the previous plan would have shipped, and what most published finance encoders do. The number long context has to beat.
2,048 Roughly a full section of prepared remarks, or a complete question and answer. Whether most of the gain arrives early.
8,192 The native ceiling. A whole MD&A subsection or a long transcript exchange. Whether the last stretch is worth the compute.

Every task runs this ladder on validation data, three seeds each, with everything else pinned. The winner becomes that task's shipped configuration. If 512 wins, that ships and the write-up says so plainly.

Long context is a hypothesis, and it can lose. The claim under test is that reading more of the document raises macro-F1 on cases where the evidence is not adjacent. The refutation is simple: if 8,192 does not beat 512 outside the noise band on the long-evidence subset, long context did not help on this task, and that gets published as the result. See definition of done for the gate.

What the labels actually mean

Label codebooks

Decided

These rules are the product. Weights are replaceable, a clear label definition is not. Every rule below has to survive contact with a real annotation round, and the rule wins over intuition when they disagree.

Aspect sentiment

LabelRuleExample
positive The text implies the aspect is doing better, or is expected to do better, than the stated or implied reference point. "Margins expanded 200bps" → aspect margins
negative The text implies the aspect is doing worse, or is expected to do worse, than the stated or implied reference point. "Cloud revenue missed consensus" → aspect cloud revenue
neutral The aspect is mentioned with no evaluative direction, or the text is purely descriptive, or the direction is genuinely ambiguous. "Revenue was $4.1bn" → aspect revenue

Hard rules

  • Sentiment is for the aspect, not the sentence. "Costs fell sharply" is positive for the company and, with aspect costs, still positive, because lower costs are good. Judge the effect on the aspect's owner.
  • A bare number is neutral. Magnitude alone is not direction. Direction needs a comparison, stated or obvious.
  • If the aspect is absent from the text, the example is invalid. Drop it. Do not label it neutral.
  • Do not import outside knowledge. If you need to know last quarter's number and the context does not give it, the answer is neutral.

Known hard cases

  • Two aspects, opposite polarity. "We gained share while pricing weakened" is two separate examples with two labels. That is the point of the task.
  • Quoted opinion. "Analysts called the guidance disappointing" is negative for the guidance. Report the sentiment in the text, not your view of it.
  • Risk-factor boilerplate. Filing risk language mentions bad things that have not happened. Neutral unless the text says the risk has materialised.
  • Beat but guided down. Label per aspect. The quarter is positive, the guidance is negative. Never average them.

Forward-looking

Test: does the sentence assert something about a state of the world that has not happened yet, at the time the text was written?

forward_looking

  • Guidance, outlooks, targets, plans, and expectations.
  • Hedged predictions. "We expect", "should", "we anticipate" all count.
  • Conditional futures. "If demand holds, we will expand capacity."
  • Announced-but-not-completed actions. "The acquisition is expected to close in Q4."

not_forward_looking

  • Reported results, historic comparisons, completed events.
  • Present-tense description of current state. "Inventory stands at 42 days."
  • Timeless statements of policy or definition.
  • References to somebody else's past forecast. "Consensus had expected 4%." That is a reported fact about the past.
  • Tense is a hint, not the rule. "Capacity comes online next quarter" is present tense and forward-looking.
  • Legal safe-harbour boilerplate is forward-looking. It is dull, it is frequent, and excluding it would be a judgement call the model cannot learn. Include it, and report how much of the positive class it is.
  • Split-nature sentences take the positive label. If any clause makes a claim about the future, the sentence is forward-looking.

Fact versus opinion

Test: could a careful reader, with access to the right source, establish that this is true or false? If yes it is a fact, even if it turns out to be wrong.

fact

  • Reported numbers, dates, named events, filed figures.
  • Attributed statements. "The CFO said margins would improve" is a checkable fact about what was said.
  • False or disputed claims that are still checkable.
  • Definitions and stated methodology.

opinion

  • Evaluations. "Strong quarter", "disappointing execution".
  • Recommendations and ratings.
  • Unattributed predictions and estimates of value.
  • Causal claims presented without evidence. "Weakness was driven by macro softness."
  • Truth is not the test. Checkability is. A wrong number is still a fact.
  • The mixed-sentence rule. If a sentence states a checkable thing and then judges it, label it opinion. The judgement is the part a downstream consumer must not treat as evidence. Write this rule into the annotation tool so it is applied every time.
  • Attribution flips it. "Margins will improve" is opinion. "Management said margins will improve" is fact.
  • Overlap with forward-looking is expected. The two labels are not independent, and the write-up must report the confusion between them rather than pretend they are separate.

The codebook is versioned. It lives at docs/codebook/ in the repo, one Markdown file per task, with a version number. Every labelled example records the codebook version it was labelled under. A codebook change without a version bump is a bug.

What this is not

Non-goals

Enforced

Each of these was considered and dropped. They are listed so that nobody, human or agent, quietly adds them back. Adding one back needs a decision-log entry.

Aspect extraction

The ABSA model takes an aspect as input. Finding aspects in raw text is a separate problem with separate data and separate metrics.

Not in this project

Entity reasoning claims

The previous project conditioned on entities and then claimed the model reasoned about them. It did not. Feeding an aspect string in is conditioning, and the write-up must say only that.

Do not claim

Anything past 8,192 tokens

8,192 is the ceiling, because it is what the base encoder was pretrained for. Whole 10-Ks, multi-document reasoning, hierarchical chunk aggregation and retrieval all sit outside it. The caller cuts the document into passages.

Hard limit

"Long context works" as an assumption

Length is on the experiment ladder, not in the conclusion. Every task publishes 512 against 8,192 with intervals, and a task where the short model wins ships as the short model.

Measure, never assume

A multi-task model

Three separate models. A shared trunk makes gains impossible to attribute and every release couples to the other two.

Rejected

General-domain coverage

Finance only. Out-of-domain behaviour may be measured and reported, and it is never a claim.

Out of scope

Numeric sentiment scores

Discrete labels with probabilities. Continuous sentiment scores from FiQA and SemEval get thresholded into classes, and that mapping gets documented.

Not an output

Calibration claims

Calibration numbers get reported. "The model is well calibrated" was quarantined last time and stays quarantined until a reliability curve on the gold set says otherwise.

Report, never claim

Machine-labelled test data

Training labels come from an ensemble of routed models. Test labels never do. A model scored against labels its own teachers produced cannot tell you anything about whether it beat them.

Human gold only

A production service

This is a research release. A demo Space and a clean inference example, and no SLA, no hosted API, no uptime promise.

Not shipped

Who uses the output

Users and jobs

Assumed

The primary reader of this document is whoever builds the project next, including future you and coding agents. These are the downstream users the models are shaped for.

Research and quant teams

Score thousands of transcript sentences per company per quarter. Needs cheap batch inference and a stable label meaning across versions. Cares about recall on forward-looking above everything.

Anyone building finance RAG

Wants to tag retrieved chunks so a generator can separate reported fact from analyst view, and history from guidance. Needs low latency per sentence.

NLP practitioners and reviewers

Wants to reproduce the numbers, check the protocol, and reuse the gold sets as a benchmark. Cares more about the evidence trail than the headline score.

Not a target user: retail investors, anything giving financial advice, and any use where a wrong label carries direct money risk without a human in the loop. This gets stated in every model card.

The bar

Definition of done

Decided

Success is matching what a routed ensemble of large models can do on a frozen human gold set, reading the same passage they read, at a tiny fraction of the cost. Each of the three models clears the bar on its own. A model that misses still ships, with the miss stated in the card.

Weak supervision changes what "beating the LLM" means

Training labels now come from k different models voted together. The student is distilled from an ensemble that contains the single-model baseline. Beating that single model is therefore expected, and it is a weak claim.

The honest headline is against the ensemble: a 150M encoder reaches the quality of k routed frontier models, on the same passages, at a fraction of the cost and latency. The single-model comparison stays in the table, labelled as what it is, which is a distillation result.

The long-evidence subset. Every gold set is tagged at annotation time with whether the label needed evidence outside the target sentence, and roughly how far away it was. That tag splits the test set into a near half and a long half. Headline numbers are reported on the whole set and on both halves. Without this split, a long-context gain averages away into nothing and nobody can tell whether the extra tokens did anything.

Gate Requirement Applies to
Quality Macro-F1 on the frozen gold test set is at or above the routed ensemble's own macro-F1 on that same set, tested as a paired bootstrap of the per-example difference. "At or above" means the interval on the difference does not put the ensemble clearly ahead. Every model in the ensemble gets the same passage the student got. Each model
Length ladder The 512, 2,048 and 8,192 configurations are all trained and all reported, three seeds each, on the whole gold set and on both halves of the long-evidence split. The shipped length is whichever won on validation, and the losing lengths stay in the table. Each task
Truncation Measured truncation rate at the shipped length is recorded and under 5%. Above that, the run is blocked before it starts. This is the gate the previous project did not have. Each dataset
Cost Measured cost per 1,000 passages is at least 50× lower than the routed ensemble, counting real token usage at recorded prices, over identical passages. Labelling and training cost is reported separately and is not netted out of this ratio. Each model
Latency Median latency per passage is measured and published at every length on the ladder, on the reported hardware and on CPU, with batch throughput at the largest batch that fits. The gate is under one second per passage at the shipped length. Under 50ms still holds at 512 and that number stays in the table. Each model
Label quality The weak-supervision label model beats both plain majority vote and the best single labelling function, measured on a human-labelled development set that is separate from the test set. Each task
Human ceiling Inter-annotator agreement on the gold set is measured and published. Model scores are read against that ceiling, never against 100%. Each task
Reproducible A clean checkout plus one documented command reproduces the reported test numbers within noise, from the released checkpoint. Each model
Traceable Every training example carries its source, licence, and how it was labelled, including which labelling functions voted and what the label model returned. No example with unknown provenance is in any training set. Each dataset
Published Weights, datasets, code, model cards, and the write-up are public, with matching numbers in all four. The project

Every gate is measured on the frozen gold test set, never on validation data. The gold set is built before any model is trained and is not looked at during development.

Baselines every model is measured against

  • Majority class. The floor. Catches a broken metric.
  • TF-IDF plus logistic regression. The cheap classical baseline. If a fine-tuned encoder cannot clearly beat it, the task is trivial or the data is broken.
  • The same encoder at 512 tokens. The internal control for the whole long-context claim. Identical data, identical recipe, shorter input. Any long-context gain is measured against this and nothing else.
  • The routed ensemble. All k models voted through the label model, over the same passages, scored on the gold set. This is the teacher, and it is the number that matters.
  • Each single model in the ensemble. Few-shot, one row per model, prompt tuned on the development set only. Shows which teachers carried the vote.
  • Zero-shot single model. Reported to show what prompt work is worth.
  • Off-the-shelf finance encoder. Existing public models on the same task where one exists, to show the delta from doing this properly.

What is deliberately not a gate

  • Beating published state of the art. Prior benchmark protocols are not comparable to this one, and forcing the comparison is how the last project produced numbers it had to retract.
  • A round number like 90%. The gold set defines the ceiling, and it is unknown until agreement is measured.
  • Long context winning. The ladder is run and published either way. A task where 512 wins is a real finding, and it ships as the short model with the ladder in the card.
  • Calibration quality. Reported, not gated.
  • Out-of-domain robustness. Measured and published as a limitation, not a pass condition.

Every comparison is paired

The gold set is 1,000 examples, and the long-evidence split cuts each headline into halves of a few hundred. At those sizes a single model's own confidence interval spans several points, and two overlapping intervals say almost nothing about which model is better.

So nothing is compared that way. The student and its comparator are scored on the same examples, and the bootstrap runs over the per-example difference. That cancels the shared difficulty of the examples and resolves gaps far smaller than the individual intervals suggest. It matters most exactly where this project needs it: the student against the ensemble, and 8,192 against the 512 control on the far half.

Carried over from the last project

Evidence rules

Non-negotiable

Every number in this project carries a grade. The grade travels with the number into the model card, the write-up and the README. An ungraded number is not publishable.

Supported

A saved run with a config, a seed, a logged artifact, and an evaluation on the frozen gold set. Safe to put in a headline.

Reported

A number that exists in a log or a notebook but has no reproducible artifact behind it. Usable in the text with the caveat attached.

Compromised

A run with a known protocol problem such as leakage, a changed test set, or an unrecorded preprocessing step. Kept for the record, never quoted.

Not run

Planned and not executed. Named explicitly so an unrun experiment never quietly becomes a claim.

The single rule that matters. If the protocol changed, the number is not comparable, no matter how much better it looks. The last project learned this expensively. Protocol first, headline second.

Learned the hard way

Known traps

From learnings.html

These are failure modes the previous project actually hit. Each one has a countermeasure baked into the plan rather than a warning to be careful.

TrapWhat happened beforeCountermeasure here
Protocol drift Evaluation protocol changed between runs, so headline gains were not comparable and had to be withdrawn. Gold test sets are frozen and hashed before the first training run. The eval harness refuses to run against an unrecognised hash.
Silent data mixing Human and augmented data merged in a way that could not be reconstructed afterwards. Every row carries a provenance field. Mixing happens in a config, not in a notebook. A test fails if provenance is missing.
Split leakage Near-duplicate sentences appeared across train and test splits. Near-duplicate detection across splits runs in CI and fails the build.
Unfalsifiable claims "Entity-aware" and "well calibrated" were asserted without a test that could have disproved them. Every claim in the write-up names the experiment that could refute it. No experiment, no claim.
Notebook-only runs Notebook source was treated as proof a run happened, and the run could not be reproduced. Training runs write a registry entry with config hash, seed, and artifact path. No registry entry means the run did not happen.
Long context on broken data A long run trained on rows that were still 52.8% truncated at 6,144 tokens. The conclusion drawn was that length did not help. What was actually measured was that the examples were malformed. Truncation rate is measured before the run and asserted under 5%. The passage builder has its own test suite. Length only enters the argument once the data is known to be intact.
Long context assumed to help The opposite failure, and the one this project is now exposed to. Extra tokens feel like they must be worth something. 512 is trained as an internal control on every task. The long-evidence split is where the gain has to show up. No gain there means no claim.
Augmentation causality A gain was attributed to a data-generation method without an ablation that isolated it. Synthetic data is out of the default plan. If it is added, it runs as a controlled A/B on one task with everything else fixed.
Correlated teachers New risk. The label model assumes its labelling functions fail independently. Large models trained on overlapping data fail in the same places, so k of them agreeing is weaker evidence than it looks. Pick models from different families. Add non-LLM heuristic labelling functions. Measure pairwise agreement on the human development set and report it next to every label-model number.
Label model theatre New risk. A learned label model feels more rigorous than counting votes, and on highly correlated inputs it often is not better. Plain majority vote is a required baseline for the label model. If it wins, use it, and say so.
Distillation dressed as victory New risk. Training on ensemble labels and then claiming to beat one of its members is close to circular. The headline comparison is against the ensemble. Single-model comparisons are labelled as distillation results wherever they appear.
Long passages, large bill New risk. Labelling cost scales with passage length times the number of models. The move to 8,192 tokens multiplies the labelling budget several times over, and it is easy not to notice until the invoice arrives. A 500-row pilot at each length before any full run. A hard dollar ceiling in the runner. Response caching, so a prompt fix does not re-buy every label.
Loss-function overcorrection Inverse-frequency class weighting swung the model too far toward rare classes. Class weighting is a tuned knob measured on validation macro-F1, with the unweighted run always reported next to it.
