How the work gets run without producing numbers you have to retract

The rules everything else follows from

Operating principles

Enforced in CI

Eight rules. Most of them are enforced by a test or a script, not by discipline. Anything that depends only on remembering will eventually be forgotten.

1

Freeze the test set before training anything

The borrowed test set for a task is adopted, re-split, reconstructed, hashed and committed before the first training run on that task. Its hash goes in the config, and so does the hash of its reconstructed passages. The eval harness refuses to score against a hash it does not recognise.

2

One variable per experiment

A run changes one thing. If two things change, the run tells you nothing about either. Multi-change runs are allowed only as a deliberate "does anything work at all" probe, and they are labelled as such in the registry.

3

Provenance travels with every row

Source, licence, label origin, codebook version. A row without provenance never enters a training set. A data-loading test enforces this.

4

Never look at the test set

Prompt tuning, labelling-function selection, label-model fitting, hyperparameter search, checkpoint selection, backbone selection, threshold picking. All of it happens on the development and validation sets. The frozen borrowed test split is opened once per model, at the end.

This is affordable now. The development and validation splits carry human labels from the same borrowed source as the test split, so the number you steer by and the number you publish are the same kind of number, written by the same annotators, on the same task. Nothing about the headline is a different measurement from the one you read every day. That was not true of the interim design, where the headline was agreement with a machine-written key that validation never touched.

5

Every claim names its refutation

Before writing a claim, say what result would have disproved it. If no such result exists, the sentence is an opinion and gets written as one.

6

Report the human ceiling next to the model

A macro-F1 of 0.84 means one thing if annotators agree 0.95 of the time and something else entirely if they agree 0.86 of the time. The ceiling is always in the table.

7

Negative results ship

A model that misses the bar is released with the miss stated. A method that did not help gets a paragraph in the write-up. The project is worth more as an honest record than as a set of wins.

8

If it is not in the registry, it did not happen

A number without a registry row cannot be quoted anywhere. Not in the README, not in the model card, not in conversation. This is the rule that the last project most needed and did not have.

Sequencing

Phases

One task per phase

Each phase takes one task from raw data to a released model. The first phase also builds the shared machinery, so it is the longest by a wide margin. Detailed scope for each is in Vertical slices.

Phase 1 — Forward-looking, and the harness

First

Goes first because it has the strongest borrowed benchmark of the three, and because it is the largest. 3,600 human-labelled sentences in three classes, with a published 1,000-row test split. That keeps the risk in the machinery rather than in the task. Everything reusable is built here: data schema, input builder, weak-supervision pipeline, eval harness, run registry, baseline runners, model card template, CI.

Its real headline is the backbone bench, which runs once for the whole project. Four encoder families at nine checkpoints, three seeds each, one shared label set, one shared maximum length, nothing else moving. That picks the encoder the other two phases inherit, and the full table is a deliverable in its own right.

Exit: one released model, one adopted and frozen benchmark, the nine-candidate bench table, and a harness the next two phases use unchanged.

Phase 2 — Aspect-based sentiment

Second

Second because it adds one new thing to a proven pipeline, which is that the aspect goes into the input. FiQA 2018 supplies the benchmark, and it brings a target, an aspect taxonomy and a continuous score, so the score-to-class mapping gets decided and documented here.

It is also the phase that tests whether the Phase 1 backbone transfers. FiQA is tweets and headlines, a very different text distribution from filing prose, and it is the smallest of the three sets at 1,213 rows. If the inherited encoder underperforms the classical baseline here, the bench gets re-run on this task and both tables are published.

Exit: released model, adopted benchmark, and a documented mapping from the continuous source scores to the three classes.

Phase 3 — Fact versus opinion

Third

Last because it is the only task with no exactly matching public benchmark, so it carries the open decision described in the benchmark program. Either it becomes premise versus claim and adopts FinArg, or it keeps its current definition and ships with no accuracy number at all. With the machine-written answer key removed there is no second option any more: a task with no human-labelled benchmark has no headline. Doing it last means the pipeline is proven and priced before that call has to be made.

Exit: released model, the fork resolved in writing, and a measured overlap with the forward-looking labels.

Phase 4 — Suite release

Last

The cross-model comparison table, the demo Space, and the write-up that tests the thesis. This is where the three models stop being three projects and become one claim.

Exit: public write-up with every number graded, and a demo anyone can paste text into.

Phases do not overlap. The temptation after Phase 1 is to start all three at once. Do not. The harness will need changes discovered in Phase 2, and changing it while three models are mid-training is how protocol drift starts.

The backbone bench runs once, in Phase 1. Phases 2 and 3 inherit the winner and do not re-run the nine candidates. The one thing that reopens it is a phase where the inherited backbone lands below the classical baseline, which would say the bench answered a question about forward-looking rather than a question about the encoder. If that happens, the bench is re-run on that task and both results are published side by side.

Every task picks its own max_length, and that is not an experiment. Tokenise the task's rows, read the distribution, take the smallest supported setting that keeps truncation under 5%, record it in the config with the distribution beside it. One measurement, no training runs, no ladder.

Where labels come from

Data program

Decided

Three tracks, kept apart at every stage. They have different reliability, different licences and different failure modes. Merging them without a record is the mistake the last project made, and it made the results impossible to reconstruct.

Track A — Public labelled

Reproducible

Existing annotated datasets. Cheap, citable, and other people can check them. The catch is that none of them were labelled under this codebook, so their label meaning is close but not identical.

  • Used for training and validation.
  • Never used as the gold test set.
  • Each source gets a mapping note saying how its labels were translated.

Track B — Borrowed human

The benchmark

Published datasets whose labels were made by people, adopted whole and frozen. Nobody on this project annotates anything. This track carries the headline for every task, and it is the only place any comparison between the encoder, its teachers and a frontier model is settled.

  • Test and development only. Never trained on.
  • Frozen and hashed before training starts.
  • Source, licence and published annotator agreement recorded per set.
  • The codebook is written to fit the borrowed labels, not the other way round.
  • Small, and somebody else's definitions. Both caveats travel with every number.

Track C — Weakly supervised

Scale, with doubt

Every passage labelled by k different models through one router, plus a few cheap heuristics, combined into one probabilistic label. This is where training volume comes from, and it inherits whatever the models get wrong together.

  • Training only, in its own split.
  • One labelling run per task, at that task's chosen max_length, over training rows only. Validation and test labels come from the borrowed dataset.
  • Deliberately not frontier models. Cheap is the point, because this track is bought at volume.
  • Label quality measured against a human development set, never against the test set.
  • Its contribution is proven by an ablation, never assumed.
  • Never the bar. The student is graded on human labels, and every teacher is scored on those same rows as a baseline.

The circularity problem, and how the benchmark fixes it

The old design had one failure baked in. The models that produced the training labels were also the baseline being compared against, so a student could not cleanly beat its teachers on answers the teachers wrote.

The fix is that nothing this project runs writes a test label. Every published metric is macro-F1 against the labels the borrowed dataset's annotators wrote. The teachers write extra training rows and never touch an evaluation split. A pinned frontier model is scored on those same rows like any other baseline. So "the encoder matched or beat the frontier model" is a plain paired comparison with a named benchmark, and "the encoder beat its teachers" is another one on the same rows.

An interim design added a third role and made things worse. It had a pinned frontier model write a 5,000-passage answer key, and made agreement with that key the headline. Fidelity to one model's opinion is not accuracy, the key cost low thousands of dollars, and the frontier model scored 100% on its own key by construction, which removed the one comparison that mattered. That track is deleted.

What the borrowed sets still cost. They are small, their label definitions are somebody else's, and every LLM baseline may have read them during pretraining. All three caveats travel with every number taken from them.

Two habits survive from the old plan. Every model is reported twice, once trained without Track C and once with it. And any comparison against a single teacher is labelled a distillation result wherever it appears, including in the model card. Contamination handling stays in the benchmark program.

Rules for adopting a borrowed set

The old version of this block was sampling rules, because the gold set was going to be sampled and annotated here. It is not. What is left is the discipline that has to be applied to somebody else's sample instead, and the first rule is the one that hurts.

  • You inherit their sample, including its biases. The distribution was chosen by other people for other reasons. Measure it, publish it, and stop describing it as the target distribution. Report per-source performance where the set carries a source field, and say when it does not.
  • Do not rebalance the classes. Same rule as before. Report the natural rate and handle imbalance in training, never in the test set.
  • Deduplicate before splitting, on full text, because boilerplate repeats across filings and the borrowed sets were not deduplicated against each other.
  • Group the split by document, call or company wherever the set carries such a field. Where it does not, say so in the model card rather than implying a grouped split that was never possible.
  • Use the unit the annotators labelled. Rebuilding the surrounding passage is an optional ablation, not part of the pipeline, and never part of the headline.
  • Publish the token-length distribution per split. It is what max_length is chosen from, and it is what the truncation rate is read against.
  • Split once and freeze. Re-splitting after seeing results is the same as tuning on the test set, and it is easier to do accidentally with a borrowed set than with one you annotated yourself.

Long passages make the licence problem worse. A single sentence from a paid transcript is arguably a quotation. Two thousand tokens of it is not. Redistribution terms get checked against the passage length actually being published, not against the sentence. Where terms are unclear, publish document identifiers and character offsets instead of the text, and ship a script that rebuilds the passages from the source.

Where training labels come from

Weak supervision

Decided

Each passage goes to k different models through one router. Each model's answer is a labelling function. A label model learns how much to trust each one and returns a probabilistic label. The student trains on those. This is what makes a training set of tens of thousands of passages possible at all, and it brings its own failure modes.

1. RouteEach passage is sent to k models from different families, with the target span marked exactly as the student sees it. One prompt, one structured answer, abstention allowed.
↓
2. Add heuristicsTwo or three cheap rule-based labelling functions per task. Low coverage, high precision, and genuinely uncorrelated with the models.
↓
3. Build the label matrixOne row per passage, one column per labelling function, with abstentions marked rather than guessed.
↓
4. DiagnoseCoverage, overlap, conflict, and pairwise agreement per function, measured on the human development set.
↓
5. Fit the label modelSnorkel's label model against plain majority vote. Whichever wins on the borrowed human development set is the one used.
↓
6. Train the studentSoft labels, noise-aware loss. Low-confidence rows dropped by a threshold chosen on validation data.

One labelling run per task, and it is priced before it is bought

Labelling cost is roughly row length times the number of models times the number of rows. The borrowed rows are short, so this is now a modest line rather than the largest one in the budget. It got that way by deletion: an earlier design bought training labels separately at each of three length rungs, plus a validation key, plus a 5,000-passage frontier answer key, plus a two-condition probe over all of it.

What is left is one run per task, at the task's chosen max_length, over training rows only. Validation and test labels come from the borrowed dataset and cost nothing.

The pilot still comes first. 500 rows, real cost per row per model, coverage and empirical accuracy measured on the human development set. Gate 4 decides whether the full run is worth buying at all. If the label model cannot beat its best single labelling function, the task trains on the borrowed labels alone and the saving is recorded.

Choosing the k models

  • Different families, not different sizes. Two versions of the same model fail in the same places and add almost nothing to the vote.
  • Five is the starting point. Enough for the label model to estimate accuracies, few enough to afford.
  • Every model must handle the task's max_length. A model that silently truncates is labelling a different task from the one the student learns.
  • Pin exact model identifiers per run. Router-hosted models get updated and deprecated, so an unpinned run is not reproducible.
  • Mix strong and cheap. A weaker model with a different bias can be more useful to the vote than a second strong one that agrees with the first.
  • Record cost per model per run. One expensive function is often removable at almost no quality cost, and you can only see that if you measured it.

The heuristic labelling functions

Cheap, transparent, and the only functions in the set that are genuinely independent of the models. They matter more than their accuracy suggests.

  • Forward-looking: future modals, expectation verbs, explicit horizon phrases, safe-harbour markers, applied to the target span. Abstain otherwise.
  • Fact versus opinion: attribution patterns, evaluative adjective lists, presence of a figure with a unit. Abstain otherwise.
  • Aspect sentiment: direction verbs near the aspect mention, negation handling. Low coverage, and useful where it fires.
  • Abstaining is normal. A function that answers on 15% of rows and is right almost every time is a good function.

The assumption most likely to be violated

A label model works by assuming its functions make mistakes for unrelated reasons. Large models trained on overlapping web text do not. When five of them are wrong they are often wrong in the same way and on the same rows, and the label model reads that agreement as confidence.

What is done about it. Pairwise conditional agreement is measured on the human development set and published. Model families are chosen to be as different as the router allows. Heuristic functions are included specifically because they break the correlation. And plain majority vote is always run alongside, because if the independence assumption is badly broken the learned model has no real advantage over counting, and pretending otherwise is the kind of unfalsifiable claim this project exists to avoid.

Budget discipline

  • Pilot on 500 rows first. Measure real cost per row per model, and measure label quality on the human development set, before any full run.
  • Set a dollar ceiling per task and make the runner stop at it rather than warn.
  • Cache every response by hash of prompt plus model plus passage. A rerun after a bug fix should cost nothing for rows that did not change.
  • Drop functions that do not pay. If removing a model changes label quality by less than noise, remove it and note the saving.
  • Scale the row count to the gain. Plot student quality against training rows on validation data. Where the curve flattens, stop buying rows.
  • Buy no evaluation labels at all. Validation and test labels come from the borrowed dataset. Any spend on an evaluation split needs a decision-log entry saying why the borrowed labels were not enough.

Where the benchmark comes from now

Benchmark program

Open item inside

One test set per task, borrowed whole from a published dataset whose labels people wrote. Macro-F1 on that frozen split is the headline, and every baseline including a pinned frontier model is scored on the same rows. Nobody on this project annotates anything. This section names the borrowed sets, states what each one buys, and states what it costs.

The trade is real and it is not free. Hand annotation would have bought labels that matched our own codebook. Borrowed labels do not. The codebook has to be rewritten to match somebody else's definitions, and where those definitions differ from what this project wanted, the project's wording changes rather than the benchmark's. Forward-looking is three classes because the benchmark is three classes.

Two things this used to require, and no longer does. An interim design added a second, machine-labelled test set of 5,000 passages per task, and an evidence-distance tag on every row inferred from a frontier model. Both existed only to support a length experiment that is now removed. Deleting them takes low thousands of dollars out of the budget, removes the passage-reconstruction dependency, and makes the headline an accuracy number against human labels again.

What this settles for free

  • The aspect vocabulary question is answered. FiQA ships its own taxonomy, so aspects come from the source rather than being invented.
  • The score mapping decision has a published reference point, because FiQA ships both the continuous score and a mapped class.
  • The annotator count question is closed. There is no second annotator because there is no first one.
  • Three months of annotation comes out of the schedule entirely.

What it costs

  • The forward-looking task becomes three-class. The binary codebook in Product is rewritten to match, or the labels cannot be used.
  • No passages ship with any of the three sets. Every row is a bare sentence.
  • No evidence-distance field exists, and it cannot be added without an annotator.
  • All three sets are public and indexed, so the frontier models in the ensemble may have seen them.

Surrounding text, and why it is now optional

The borrowed sets ship the unit their annotators labelled. FLS ships single filing sentences. FinArg ships transcript turns. FiQA ships tweets and headlines. Train and evaluate on that unit. This is the honest default, because it is the unit the label was written about.

  • Rebuilding the surrounding passage is no longer required, and is no longer a gate. It was required by the length ladder. With the ladder removed, nothing in the headline depends on it.
  • The measurement that killed it is worth keeping on the record. 120 FLS test rows were queried against EDGAR full-text search restricted to form 10-K. 105 returned cleanly. Only 27% resolved to exactly one filing. For the rest the pipeline would have to pick a passage from between 2 and dozens of candidates, and the ambiguity is worst on non_specific_fls, the class the codebook calls the hard boundary.
  • If it is attempted later, it is an ablation and it is labelled one. Train with and without the recovered passage, on rows that resolve to exactly one filing, and publish both numbers with the recovery rate beside them. A gain there is a real finding. It is not the headline and it does not gate the release.

The human ceiling

Every model card carries a ceiling next to the score. With borrowed labels the ceiling is borrowed too, and where the source never published one, the card says so instead of inventing a number.

  • Quote the source paper's agreement statistic where it exists, with the citation, and say plainly that it was measured by other people on their sample.
  • Where no agreement figure was published, the card reads "not published by the source". That is an honest gap. Filling it with a guess is worse than leaving it open.
  • Run a label-noise probe as a floor. Take the rows where every model in the ensemble agrees with each other and disagrees with the borrowed label, then read a sample by hand. That sample is small enough to be an afternoon, and it gives an upper bound on how noisy the borrowed labels are.
  • An LLM is still not an annotator. The probe finds candidate bad rows. It does not decide them, and its output never becomes the ceiling.

Splitting the borrowed benchmark sets

The frozen test set

Borrowed, re-split, hashed
  • FLS. Keep the published 1,000-row test split unchanged, so published numbers stay comparable.
  • FiQA. The official 150-row test split is too small to read a result from. Pool all 1,213 rows and cut 500 for test, grouped by target company. Score the official 150 as well, and report both.
  • FinArg. One 969-row split ships. Cut 600 for test, grouped by call.

The development set

200 per task
  • Carved from the borrowed rows that are not in test, at split time, and hashed separately.
  • Still what the labelling functions, prompts and thresholds get tuned against.
  • Still never a headline number, because it has been tuned against.
  • Grouped by document or company, so a tuned-on row cannot reappear in test wearing a different sentence.

A borrowed row used anywhere else poisons the benchmark. These datasets ship train splits, and those splits are tempting free training data. Any row that lands in Track B is banned from Track A and Track C by identifier, and the harness fails the build on an overlap. Two of the sets ship no document identifier, so grouped splitting cannot be fully verified on them. Near-duplicate checking on full text is the fallback, and the model card states that document-level grouping is unverifiable for those sets.

Contamination, and where it bites. All three borrowed sets are on Hugging Face and have been for years, so every LLM baseline may have read them. The encoder's own score is not affected, because it is trained from a pinned checkpoint on known rows. What is affected is every comparison against an LLM, in the direction that flatters the LLM and makes the encoder's win look smaller than it is.

The defence, and it is partial. Score each LLM baseline on the frozen split and on a sample of fresh unlabelled rows from the same corpora, labelled by nobody, and compare the two answer distributions. A large shift is reported as suspected contamination and every LLM comparison on that task is downgraded one evidence grade. This is a flag, not a fix, and the write-up says so.

Open decision, and it changes the third product. No public dataset matches the fact-versus-opinion codebook. FinArg's premise-versus-claim labels are close in spirit but not the same rule, and its own examples show it: a sentence beginning "I think" is labelled a premise there, and would be opinion under our codebook. Two ways out. Adopt premise versus claim as the real task and rename the model, which keeps a human benchmark and a defensible accuracy claim. Or keep fact versus opinion and ship it with a distillation claim only, measured as agreement with the ensemble plus cost and latency, with no accuracy number at all. The recommendation is the first, because a published human benchmark is the thing this whole programme is built around. Decide before Phase 3 opens.

The thing you have to beat

Baseline program

Same harness as the models

A weak baseline makes a weak result look strong. The LLM baseline gets the same care as the model, or the headline claim is worthless.

Fairness rules for the LLM baselines

  • The prompt gets a real effort budget. Several iterations against the development set, not one attempt.
  • The full codebook definition goes in the prompt. Do not handicap the models by underspecifying the task.
  • Parsing failures count as abstentions in the label matrix and as errors in the baseline table. Both rates are reported.
  • Exact model identifiers are pinned and recorded, since a router can silently serve a newer version.
  • The LLM reads exactly what the encoder reads. Same row, same marked target, same trimming, done once by the same code. Handing the LLM more text than the encoder gets, or less, makes the comparison meaningless in whichever direction the difference runs.
  • Run it three times and report the spread, because even at temperature 0 the output can move.

Measuring the cost claim

  • Count actual input and output tokens for the whole test set. Do not estimate. Long passages make input tokens the dominant term, and that is the heart of the cost story.
  • Price at published list rates, with the date recorded, since prices change.
  • For the encoder, report throughput at its shipped length and the per-second cost of the GPU it ran on, so the comparison is like for like. Report CPU inference too.
  • Report cost per 1,000 rows for both, and the ratio. Then report the number that actually helps a reader: the break-even volume, meaning the monthly row count at which the encoder including its one-off labelling and training bill becomes cheaper than the API call.
  • Report the labelling spend and the training spend separately. They are the one-off half of the break-even calculation.
  • Report the setup cost prominently. The student needed a labelling run, a training run and 1,200 human labels. The ensemble needed none of that. Quote the break-even volume where the student becomes cheaper overall, because that is the number a practitioner actually needs.

What every run must record

Experiment protocol

Registry-backed

One row per run in a registry file, written by the training script and not by hand. A run without a row cannot be quoted. This is the direct fix for the previous project's reproducibility gap.

Run discipline

  • Write the hypothesis first. If you cannot say what the run tests before starting it, you are not running an experiment, you are hoping.
  • Three seeds before any comparison. A one-seed difference of a point or two is noise. Report mean and spread.
  • Checkpoint selection on validation macro-F1, evaluated often enough to catch the peak. The previous project found frequent selection helped.
  • Test evaluation is a separate deliberate step, run once per candidate model, and it writes to the registry.
  • The loop is a batch, and that is on purpose. There is no seconds-scale local metric and none is planned. See below.

When a run is compromised

  • Grade it compromised in the registry with the reason. Do not delete it.
  • Any number from it is unusable, including numbers that look good.
  • If the compromise came from a code path, add a test that would have caught it before rerunning.
  • A preprocessing assertion that stops a run is a success, not a nuisance. The last project had one fire correctly and it saved a bad result from shipping.

Permission to continue

Decision gates

Can fail

Each gate is a real stop. Failing one means fixing the cause, not carrying on and hoping the next phase covers it. A gate that never fails is decoration.

Gate1

The benchmark is admissible

The borrowed set's labels were made by people, and the source says so. Its licence permits the use and the redistribution actually planned. Its class definitions are written into our codebook verbatim, with every place they differ from the original intent recorded. Its published annotator agreement is quoted, or its absence is stated. No row overlaps any training source.

The LLM baselines are pinned too. gpt-5.6-sol at medium effort resolves on a live call, returns the version metadata expected, and its response cache is writing. Its terms of service permit using its outputs this way, which is a licence question as real as the dataset one and is easier to get wrong. This is cheap to check and expensive to skip.

If it fails: do not adopt the set. A benchmark whose labels mean something slightly different from the codebook produces a headline that means something slightly different from what it says, and no reader can detect the gap. This is now the cheapest failure in the programme and the most expensive one to skip.
Gate2

Data is clean

No near-duplicates across splits, checked on full text. Every row has provenance. Every target span resolves inside its row. Licence confirmed for every source that will be redistributed. Class rates and token-length distribution recorded per split. The published test split is byte-identical to the source's, or the re-split rule is written down and hashed.

If it fails: no training run starts. Leakage found later invalidates everything downstream of it. Note that the published FLS splits are not clean as shipped: four rows of identical text appear in both train and test, and the dedup rule must drop them from train, because the 1,000-row test split stays unchanged.
Gate3

The length budget holds

At the task's chosen max_length: trimming affects under 5% of rows, nothing within two sentences of a target is lost, and the configuration actually fits the available hardware for a full run.

If it fails: the run does not start. Fix input assembly, or raise max_length to the next supported setting and record why. This is the gate the previous project did not have, and its absence is the whole reason the earlier long-context result was uninterpretable.
Gate4

Weak labels are worth buying

On the borrowed human development set, and only that set, the label model beats both plain majority vote and the best single labelling function. Coverage, conflict, pairwise agreement and measured cost per row are all recorded.

If it fails: do not buy labels at volume. Either the functions are too correlated to combine usefully, in which case use majority vote and say so, or the prompt needs work, or the weak labels are not worth buying for this task at all and it trains on the borrowed labels alone. This is the one gate whose failure costs real money rather than time, so it runs on a 500-row pilot before the full run.
Gate5

Model beats the classical baseline

The fine-tuned encoder clearly beats TF-IDF plus logistic regression on validation data.

If it fails: stop and diagnose. Either the task is lexically trivial, which is a publishable finding on its own, or the training pipeline is broken. Do not tune hyperparameters until you know which.
Gate6

Model meets the success bar

Macro-F1 on the frozen borrowed test split, measured once, against the labels people wrote. The bar is set after the baselines run and before the test split is opened, and written into the config at that moment: beat the best non-LLM baseline outside the noise band, and land within the noise band of gpt-5.6-sol or better. A number invented before the baselines exist is a guess, and a number chosen after the test split is opened is not a bar at all.

Four more numbers are required but do not gate. The teacher ensemble on the same rows, so the weak-to-strong comparison is readable. The full nine-candidate bench table with intervals. The per-class breakdown and the confusion matrix. And the break-even volume against the frontier baseline.

If it fails: the model still ships, with the miss in the model card and an honest section in the write-up about why. What the gate blocks is the claim, not the weights: a model that misses is never described as matching a frontier model, and the write-up leads with the gap. Failing this gate does not block the next phase. Hiding it does. An encoder that lands below its own teachers is a reported result, and an informative one.
Gate7

Release is reproducible

A clean checkout plus one command reproduces the published table from the released checkpoint and the released dataset.

If it fails: nothing is published. A number that cannot be reproduced from the public artifacts is exactly the problem this whole programme exists to avoid.

The programme-level stop rule. If Phase 1 fails Gate 1, 2 or 4 twice, stop and reconsider the task definition before spending time on Phases 2 and 3. Three models built on a shaky label definition is three times the wasted effort.

And the bench stop rule. The bench exists to pick an encoder, not to be iterated. It runs once per task with one shared recipe. If the top two candidates cannot be separated outside the noise band, that is the answer: ship the cheaper one and publish the tie. Re-running the bench with a tuned recipe until a favourite wins is tuning on validation data, and it is exactly the failure mode this document exists to prevent.

There is no fast local development loop, and the programme does not need one. An earlier review called this a gap. It is now a decision. Three reasons. The development split is a few hundred human-labelled rows, so scoring it is one short forward pass on the GPU the bench already pays for, not a separate build. The main experiment is a batch of twenty-seven short runs decided once, so a metric that returned in seconds would not change how the work is done. And the stop rule above says the recipe is not tuned against validation data anyway, so a tight edit-and-rerun cycle would invite exactly the behaviour the rule forbids. What the repository does need is the registry, the config hashing and the CI data checks, and those are Slice 1 step 1.

The plans come before the code, and the repository holding only documents is the expected state. Nothing is built until the four documents agree and the open items in the decision log are closed. The first code written is Slice 1 step 1, the skeleton, and the first number produced is the token-length distribution, which needs no training at all.

Who does what

Roles and working style

Assumed

Only you can do this

  • Deciding what a result means. Especially deciding when a result is not good enough to claim.
  • Licence and redistribution calls. An agent can read the terms. It cannot accept the liability.
  • Accepting a borrowed benchmark at Gate 1. Adopting someone else's labels means adopting their definitions and their mistakes. That is a judgement call, not a check.
  • The fact-versus-opinion fork. Renaming the third task or dropping its accuracy claim changes the product, so it is not an agent's decision.
  • Reading the label-noise probe sample. Perhaps an afternoon, and the only hand-labelling left in the whole programme.
This list used to start with annotation. That was months of work and it is gone. What is left is a handful of decisions and one afternoon of reading.

Good agent work

  • Harness, scripts, tests, CI. Well-specified engineering with a clear definition of done.
  • Dataset surveys. Finding what exists and what its terms are, with links, for you to verify.
  • Baseline runners and the cost measurement plumbing.
  • The routed labelling runs, once the prompt and the model list are fixed.
  • Drafting model cards and the write-up, from registry numbers rather than from memory.

Rule for agent work. An agent may write any code and may draft any text. An agent may not decide that a number is good enough to publish, and may not put a number anywhere without its registry row and evidence grade. Any pull request that adds a number without a registry reference gets rejected.

What an agent may decide on its own

The list above says what an agent may not decide. Left at that, the project improves at the speed of your attention rather than the agent's, so here is the other half. These decisions are delegated, in writing, and each one has a rule an agent can apply without asking.

  • Picking between two configurations on validation data. Accept the new configuration when its paired-bootstrap difference against the incumbent is positive and its 95% interval excludes zero, over three seeds. Otherwise keep the incumbent. Both runs go in the registry either way.
  • Declaring a bench tie. When the interval includes zero, the cheaper checkpoint wins and the card records that the pick was made on cost.
  • Setting max_length. Smallest supported setting with measured truncation under 5%. It is a lookup against a measured distribution, not a judgement.
  • Dropping a labelling function that does not pay. Remove it when doing so changes development-set label quality by less than noise, and record the saving.
  • Stopping the row-count curve. Stop buying training rows when the last doubling moved validation macro-F1 by less than the seed spread.
  • Re-running a job that died before any training step. Infrastructure failures are not experiments.
Everything not on this list needs a person. In particular: opening the test split, setting the success bar, accepting a benchmark, any licence call, and any sentence that makes a claim. Adding an item to this list is a decision-log entry.

What will probably go wrong

Risk register

Live
RiskWhy it is likelyResponse
The borrowed labels mean something slightly different Every existing dataset was labelled for someone else's purpose, under someone else's rules, by people who are not available to ask. The gap is usually small and always invisible in the score. The codebook is rewritten to match the borrowed definitions rather than the other way round, and every known difference is listed in the model card. Gate 1 refuses a set whose definitions cannot be written down cleanly. The forward-looking task becomes three-class because of this rule.
Reconstruction fails and the long-context claim dies All three borrowed sets ship bare sentences. The long-context claim now depends on matching those sentences back into source documents that may be missing, revised, or paywalled. Measure the match rate first, at Gate 2, before any training run. Below 60% the task ships a sentence-level headline and says so. FiQA has no document to recover at all, so that task is planned as sentence-level from the start rather than discovering it late.
An LLM baseline has memorised the benchmark All three borrowed sets are public and have sat on Hugging Face for years. Every metric in this project is measured on them, so an LLM baseline that memorised the answers inflates every comparison against it, in the direction that makes the encoder look worse. Score each LLM baseline on the frozen split and on fresh unlabelled rows from the same corpora, and compare the answer distributions. A large shift is reported as suspected contamination and every LLM comparison on that task drops one evidence grade. This is a flag, not a fix.
Fact versus opinion has no matching public benchmark It is the least studied of the three in a finance setting, and the nearest public set labels premise versus claim, which is a different question. An open decision, stated in the benchmark program. Either rename the task to premise versus claim and keep a human benchmark, or keep the current definition and ship with no accuracy number at all. With the machine-written key removed, the second branch means shipping with no headline, so the recommendation is now firmly the rename. Phase 3 runs last, so there is time to decide.
The borrowed test sets are small FiQA ships 150 test rows and FinArg ships 969 in one split. Confidence intervals on a 150-row three-class test are wide enough to swallow most differences worth reporting. Re-split FiQA and FinArg into larger test sets, grouped by company or call, and check the real group sizes before committing to a target split size. Report the official split as well so published comparisons stay possible. Where an interval is too wide to separate two bench candidates, say the bench was inconclusive and ship the cheaper one rather than picking the higher number.
The encoder cannot reach the bar It trains partly on cheap teacher labels. If the teachers are wrong in a consistent way, the encoder inherits that bias and no amount of training closes it. Set the bar from measured baselines rather than from a round number, and set it before the test split is opened. Gate 4 already measures teacher quality on the human development set, so a bad teacher pool is caught before the full labelling spend, and the task can fall back to training on the borrowed labels alone.
The student beats its teachers and nobody believes it Weak-to-strong sounds like a bug. A student trained on noisy cheap labels scoring higher than the ensemble that produced them is the expected behaviour of a label model that denoises, but it reads as leakage. Make it falsifiable rather than asserting it. Publish the teacher ensemble, each single teacher, plain majority vote, and the encoder, all scored on the same frozen human-labelled split. Gate 4 already proves the label model beats its best member, so the mechanism is documented before the result appears.
The frontier baseline is deprecated Hosted models get retired, renamed and silently updated, so the published comparison would become unreproducible. The cached responses are the artifact, not the model. They are frozen, hashed and published with the results, so the comparison table can be checked after the model is gone. Re-running with a newer model is a new row, never a refresh. The headline itself does not depend on this, because the headline is measured against human labels.
Labelling spend runs away k models across tens of thousands of rows, re-bought every time a prompt changes. Much smaller than it was, because the per-rung buying, the validation key and the 5,000-passage frontier key are all gone, but still the only line that spends real money. A 500-row pilot before the full run. A hard dollar ceiling in the runner. Response caching keyed by prompt, model and row. A learning curve that says when to stop buying rows. Gate 4 can also decide the answer is zero rows.
Router models change underneath you Hosted models get updated, deprecated and silently reassigned. A rerun months later is not the same experiment, and long-context support in particular varies between versions. Pin exact model identifiers per run and record them. Cache all responses. Treat a model list change as a new experiment with a new registry row, not a rerun of the old one.
The backbone bench comes out flat Nine checkpoints on one task with a 200-example development set is not much resolution. Modern encoders of similar size often land within a point of each other on a single classification task. That is a publishable result, and it is a cheap one. It is also now the project's main table, so a flat bench is a finding rather than a failure: it says that on this task, at this data scale, the backbone does not matter and practitioners should pick on cost. If the top few sit inside each other's interval, the cheaper checkpoint ships and the card says the pick was made on cost. Do not run more seeds hunting for a separation that is not there.
NeoBERT will not export or will not take LoRA It ships custom modelling code loaded through trust_remote_code, so the ONNX path and the LoRA target-module names are both untested here. Find out in the bench, not at release. Pin the revision so the code cannot move underneath a rerun. If it will not export, it stays in the accuracy table and is not offered as the CPU model, stated plainly. If it will not take LoRA, run it as a full fine-tune and label that row as the different recipe it is.
The CPU export work eats a week and returns nothing ONNX conversion and quantisation fail in ways that have nothing to do with the research question, and NeoBERT's custom modelling code is the likeliest to fight back. It is easy to sink days into a number that decides nothing. CPU inference is optional. Try the plain PyTorch path first, timebox anything harder, and drop it the moment it resists. The cheap-inference claim stands on the GPU and router numbers, which are measured anyway. Where no CPU number was taken, the cards say nothing about CPU speed rather than guessing.
Long passages leak across splits Boilerplate repeats across filings, so two rows from different documents can share most of their text. The published FLS splits already contain four rows of identical text in both train and test. Near-duplicate checks run on full text, not targets, and they fail the build. Dedup drops from train, never from the published test split. Grouped splitting by document stays in place on top of that.
Licences block the dataset release Financial text is commercially valuable and often restricted, and borrowed datasets carry their original terms with them. Two of the three adopted sets have no licence declared on the hub at all. Confirm terms at Gate 1, before adoption, not after training. Where terms are unclear, release row identifiers and our split assignment rather than the text itself, and link to the original set rather than mirroring it.
Scope creep back into non-goals Aspect extraction, whole-document modelling, hierarchical chunk aggregation and the length ladder all feel like natural next steps once the pipeline works. The non-goals list in Product, plus the rule that adding one back needs a decision-log entry. 8,192 is the ceiling and the caller cuts documents into passages. The length ladder in particular is removed on purpose and is named in the non-goals.
The thesis turns out to be wrong Three labels may simply not cover as much of finance NLP as claimed. That is a finding. The write-up has a section for what the three labels miss, and it gets written whatever the answer is.

The output that outlives the models

Write-up plan

Phase 4

Written from the registry, not from memory. Every number traceable to a run row. The structure is fixed now so the results cannot quietly reshape the argument later.

Sections

  1. The thesis, stated as a claim that could be wrong.
  2. The three tasks, with the full codebooks.
  3. The protocol, before any results. Deliberately first, so the reader judges the method before seeing the numbers.
  4. Data, including the tracks and their reliability.
  5. Results, one table per task, every baseline, every interval, the human ceiling in the same table.
  6. Which encoder, and does it matter, the full nine-candidate bench on all three tasks with intervals, plus the parameters-versus-score curve from Ettin's four sizes. This is the write-up's actual contribution and it gets its own section whichever way it comes out, including flat.
  7. Cost and latency, with the break-even volume against the frontier baseline, and the training and labelling cost stated too.
  8. What did not work, at similar length to what did.
  9. Thesis test, taking real finance NLP tasks and showing coverage and gaps.
  10. Limitations and quarantined claims.

Rules for the text

  • No number without an evidence grade.
  • No comparison across different protocols, ever, even with a caveat.
  • Confidence intervals in every results table, not just the text.
  • The word "state of the art" does not appear.
  • Where an earlier plan changed, say so and say why. The move from 512 tokens to 8,192 is the largest such change and it gets its own paragraph, including what the previous project's long-context failure did and did not show.
  • "Long context helps" is never written without the control run, the interval, and the evidence-distance split next to it.
  • The thesis section reports what the three labels miss, in the same detail as what they cover.
