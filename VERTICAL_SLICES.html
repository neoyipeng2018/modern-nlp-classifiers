Four slices, each one ending in something released

One task per slice, taken all the way from raw text to public weights. Nothing is built for a later slice until a slice needs it. The first slice carries the shared machinery, which makes it much larger than the other two, and that is the deliberate trade.

Slice shape

Every slice ends with a public model, a public dataset, and numbers in the registry. A slice that ends with only code is not finished.

How the cuts were made

Slicing rules

One task per slice

What every slice must do

  • Go end to end. Raw text, labels, splits, training, evaluation, release.
  • End with something published, not something ready to publish.
  • Pass every gate in Program design before the next slice starts.
  • Leave the shared harness usable by the next slice without modification, or record what had to change and why.

What no slice may do

  • Build machinery for a later slice on the grounds that it will be needed. It will be needed differently.
  • Start before the previous slice's model is released.
  • Skip the annotation because the public data looks good enough.
  • Ship a number without a registry row.

Slice 1 is roughly half the project. That is not a planning error. Choosing one slice per task means the shared harness has to live inside the first task rather than in a separate foundation phase. The cost is a long first slice. The benefit is that the harness gets designed against a real task instead of an imagined one.

The long one

Slice 1 — Forward-looking, and the harness

Start here

Slice 1

Ship modernfin-fls, and everything the other two slices reuse

Not started

Forward-looking goes first because its label definition is the easiest to write down and defend. That keeps the risk concentrated in the machinery, where you can see it, rather than in the task definition, where it hides.

New in this slice

  • Everything. Data schema, ingest, splits, input builder, training loop, evaluation harness, registry, baselines, cards, CI.
  • The first codebook and the first annotation round.
  • The T4 stability check for the chosen encoder.

Deliberately deferred

  • The aspect field. Schema has a place for it, and nothing uses it yet.
  • The demo Space.
  • Silver LLM labelling, unless public data turns out to be thin.
  • Any cross-task comparison.

Done when

  • modernfin-fls is public with a complete card.
  • The gold set is public with per-annotator labels and agreement statistics.
  • Every baseline number is in one comparison table with intervals.
  • Cost and latency are measured, not estimated.
  • A clean checkout reproduces the headline table.
  • The harness is ready for Slice 2 with no known task-specific hacks.

Risks specific to this slice

  • fp16 instability on the T4 forces an encoder change. Checked at step 2 precisely so it costs a day, not a phase.
  • Public FLS labels may not be obtainable on usable terms. If so, the training set leans on silver labels, and that gets said in the card.
  • The task may be largely lexical. If TF-IDF gets close to the encoder, that is a genuine finding, and Gate 3 exists to make you stop and check rather than tune past it.
  • Annotation fatigue on the first ever 1,000-item round. Shuffle, sit in blocks, and measure the drift.
Exit gate: Gates 1 through 5 all pass. Slice 2 does not start until the FLS model is public. If Gate 4 fails, the model still ships with the miss recorded, and Slice 2 still starts.

One new thing on a proven pipeline

Slice 2 — Aspect-based sentiment

Second

Slice 2

Ship modernfin-absa

Not started

Second because it changes exactly one part of a pipeline that already works: the aspect goes into the input as a first segment. Everything else is Slice 1's code running on different data.

New in this slice

  • The aspect field, in the schema, the input builder and the library surface.
  • Three classes instead of two, which changes the metric breakdown and the confusion reporting.
  • A documented mapping from continuous sentiment scores in public sources to the three classes.
  • Multiple examples per sentence, one per aspect, which the leakage check must understand.

Reused unchanged

  • Ingest, splitting, dedup, provenance.
  • Training loop, checkpointing, resume.
  • Evaluation harness, registry, report cards, release scripts.
  • Baseline runners, with a new prompt and new few-shot examples.
  • The context setting chosen in Slice 1, unless the ablation is rerun.

Work in order

#StepWhat it produces
1Source surveyWhat the aspect-level financial sentiment sets actually contain, in what format, under what terms. Verified by you.
2Score mapping decisionThresholds turning continuous scores into positive, negative and neutral, decided on validation data and written down before use. This choice materially shapes the results, so it is a documented decision, not an implementation detail.
3Codebook v1 and pilotThe ABSA codebook with the hard cases from the product spec, plus two pilot rounds. Expect more disagreement than FLS, because three classes and a target are harder than a binary judgement.
4Aspect selection ruleHow aspects get chosen for gold examples. Whether they come from the source dataset, or you name them during annotation. This settles the open "aspect vocabulary" question in the product spec.
5Gold annotation1,000 aspect-sentence pairs, 300 double-annotated. Includes deliberate multi-aspect sentences, because those are the ones the task exists for.
6Freeze, hash, split checksSame as Slice 1, with the added rule that all aspects of one sentence stay in the same split.
7Input builder extensionAspect as first segment, with tests for an aspect that contains marker-like text and an aspect absent from the sentence.
8Baselines and trainingSame runners, new prompts. Then LoRA fine-tune, three seeds, architecture control.
9Multi-aspect diagnosticA held-out set of sentences carrying two aspects with opposite labels, scored separately. This is the evidence that the model uses the aspect rather than the sentence, and it is the honest version of the entity claim the previous project could not support.
10Final evaluation and releaseAs Slice 1.

The multi-aspect diagnostic is the interesting result in this slice. A model can score well on aspect sentiment by ignoring the aspect entirely and reading overall sentence tone. The only way to know is to test sentences where the aspects disagree. If accuracy collapses there, the model is doing sentence sentiment with extra steps, and the card must say so. Run it before writing any claim about aspect awareness.

Done when

  • modernfin-absa is public with a complete card.
  • The gold set is public, including multi-aspect examples.
  • The score mapping is published alongside the dataset.
  • The multi-aspect diagnostic result is reported, whatever it says.
  • Clean-checkout reproduction passes.

Risks specific to this slice

  • Score thresholds decide the result. Different mappings give different headline numbers. Pick once, on validation, and publish the choice.
  • The neutral class is the hardest. It absorbs everything ambiguous, and it will dominate the confusion matrix. Report per-class numbers, not just macro-F1.
  • Public microblog data is a domain shift from filings. Useful as an out-of-domain check, misleading if it silently becomes most of the training set.
  • The model may ignore the aspect. Caught by the diagnostic, not by the headline metric.
Exit gate: Gates 1 through 5, plus the multi-aspect diagnostic run and reported. A missing diagnostic blocks release, because without it the model card cannot honestly describe what the model does.

Weakest data, strongest pipeline

Slice 3 — Fact versus opinion

Third

Slice 3

Ship modernfin-factop

Not started

Last because there is little usable public finance data for it. That makes it the slice that leans hardest on your own annotation and on LLM silver labels, so it runs when both of those are already proven.

New in this slice

  • The silver labelling pipeline at volume, with its human-reviewed accuracy sample.
  • The with-silver and without-silver ablation, reported as two results.
  • The overlap analysis against the forward-looking labels.

Reused unchanged

  • Everything from Slices 1 and 2 except the aspect field.
  • The binary metric setup from Slice 1.
  • The whole release path.

Work in order

#StepWhat it produces
1Codebook v1 and pilotThe checkability test, the attribution rule, and the mixed-sentence rule. Pilot hard, because this is the label most likely to feel obvious and turn out not to be.
2Gold annotation1,000 sentences, 300 double-annotated, sampled to include plenty of analyst text where opinion is dense.
3Silver prompt developmentAn LLM prompt built against validation data, measured against a human-labelled sample so its accuracy is a number, not a hope.
4Silver labelling runSeveral thousand labelled sentences from filings and transcripts, cached, in their own split, tagged label_source: llm.
5Two training tracksOne model without silver data, one with. Both evaluated. Both published in the card. The headline claim uses the one without.
6Baselines and final evaluationAs before.
7Overlap analysisRun the FLS model and this one over the same sentences and report the joint distribution. Shows how independent the two labels really are.
8ReleaseAs before, with the silver data published separately from the human data.

Watch the circularity here more than anywhere. This is the slice where the LLM both generates training labels and serves as the baseline to beat. The two-track training and the human-only test set are what keep the comparison meaningful. Do not let convenience collapse them into one number.

Done when

  • modernfin-factop is public with a complete card.
  • Both the with-silver and without-silver results are published.
  • Silver label accuracy against human labels is measured and stated.
  • The overlap with forward-looking is reported.
  • Clean-checkout reproduction passes.

Risks specific to this slice

  • Agreement may be low. Fact versus opinion feels obvious and is not. If kappa comes in under 0.6, rewrite the codebook before training, however tempting it is to push on.
  • Silver labels may not help. That is a publishable ablation result, and it is a better outcome than an unproven claim.
  • The labels may overlap heavily with forward-looking. If most forward-looking sentences are also opinion, part of the thesis needs restating. Report it either way.
  • Fatigue. This is the third annotation round and the least novel. Budget for it honestly rather than rushing the set that anchors the whole task.
Exit gate: Gates 1 through 5, plus both training tracks reported and the silver accuracy measured.

Three projects become one claim

Slice 4 — Suite release

Last

Slice 4

The write-up, the demo, and the thesis test

Not started

Three released models is three separate results. This slice is what turns them into an argument, and it is also where the argument gets tested rather than asserted.

What gets built

  • The Triad library surface, loading all three models with one call.
  • The demo Space, with all three outputs and the context window shown.
  • The cross-model comparison table, generated from report cards.
  • The public write-up, following the fixed structure in Program design.

The thesis test

  • Take a set of real finance NLP tasks. Screening transcripts for guidance changes, ranking analyst notes, filtering RAG chunks, and so on.
  • For each, say what the three labels give you and what they do not.
  • Publish the gaps at the same length as the coverage.
  • If the thesis does not hold, say what a fourth classifier would have to do.

Done when

  • The write-up is public with every number graded and traceable.
  • The demo is live and anyone can paste text into it.
  • The README reproduces the headline table in one command.
  • The quarantine section lists claims that were tested and dropped.
  • The thesis section reports coverage and gaps honestly.

Risks specific to this slice

  • Numbers drift between documents. Prevented by generating every table from report cards rather than typing them.
  • The write-up quietly softens a negative result. Prevented by writing the protocol section before looking at the results section.
  • The demo becomes a maintenance obligation. Keep it small, and say in the README that it is a demo with no uptime promise.

The reasoning behind the sequence

Why this order

Assumed
TaskLabel difficultyPublic dataNew machineryPosition
Forward-looking Lowest Some All of it First. The simplest label definition means the machinery gets built against a task that will not itself be the source of confusion.
Aspect sentiment Medium Most One thing Second. Best public data of the three, and it adds exactly one new mechanism to a working pipeline.
Fact vs opinion Highest Least Silver pipeline Third. Needs the annotation process and the silver pipeline to be proven, and both are proven by then.

The alternative that was rejected. Starting with aspect sentiment, because it has the best public data and continues the previous work most directly. Rejected because it would put the hardest input format and the new machinery in the same slice, and when something failed you would not know which one caused it.

Concretely, next

Where to start

Slice 1, steps 1 to 3

Three things unblock everything else, and two of them can run at the same time. None of them needs a decision that has not already been made.

Do1

Answer the three open questions

Is a second annotator available. What licence the repo will carry. Where ABSA aspects come from. The first one changes how every model card reports its ceiling, so it is worth settling before annotation starts rather than after.

Output: three decision-log entries in Product.
Do2

Run the T4 smoke check

A few hundred steps of ModernBERT-base at 512 tokens in fp16 on a free Colab T4, watching for NaN and for missing kernels. This is the largest hardware unknown in the plan and it is cheap to resolve.

Output: either the encoder choice is confirmed, or it moves to DeBERTa-v3-base with the reason recorded.
Do3

Survey the forward-looking data

What annotated FLS data exists, what it contains, and what its terms permit. An agent can gather the candidates with links. You verify them, because a licence read wrong here is discovered at release time, which is the worst possible moment.

Output: a source table with a yes or no per source, and a training data plan for Slice 1.

Then write the codebook. Everything after step 3 depends on the label definition being written down and pilot-tested. It is the least technical work in the project and the highest leverage. Nothing else should start before it.
