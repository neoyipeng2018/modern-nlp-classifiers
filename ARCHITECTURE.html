One pipeline, three models, no path around the protocol

The technical design. A shared harness that all three tasks run through unchanged, a data schema that makes provenance impossible to lose, and a training setup that fits inside a free Colab T4. Where a choice is forced by the hardware, that is said out loud.

Constraint

Every decision here is shaped by one thing: a free Colab T4 with 16GB and a session that can vanish. If a design cannot survive a lost session, it is the wrong design.

How the pieces fit

System shape

Shared across all three tasks

One pipeline, parameterised by task. The task defines its label set, its input builder and its data sources. Everything downstream of that is identical code, which is what makes the three results comparable to each other.

1. IngestRaw documents in, sentences out. Sentence splitting, deduplication, document and position recorded on every row.
↓
2. LabelThree tracks. Public sets are mapped to the codebook. Gold is annotated by hand. Silver is labelled by an LLM. Each writes its own provenance.
↓
3. Split and freezeGold becomes the test set and is hashed. Training and validation splits come from the other tracks. Leakage checks run here and can fail the build.
↓
4. Build inputsTarget sentence plus context window, aspect injected for ABSA, truncated to 512 tokens by a rule that never cuts the target.
↓
5. TrainConfig-driven fine-tune on a T4. Writes a registry row, checkpoints to Drive, resumes after a dropped session.
↓
6. EvaluateSame harness for the model and every baseline. Checks the gold hash before it will score anything. Emits one report card.
↓
7. ReleaseWeights, dataset and model card to Hugging Face, with numbers copied from the registry rather than retyped.

Where things live

Repository layout

Python package, not a notebook

Notebooks are for running things on Colab and for demonstrating things to readers. They are never where logic lives. The previous project learned this when notebook source was mistaken for proof that a run happened.

The notebook rule. A notebook may import from src/triad, set a config path, and call a function. If a notebook contains a training loop, a metric calculation or a data transformation, that is a bug to be fixed, not a style preference.

One row, everything you need to trust it

Data schema

Provenance enforced

A single schema for all three tasks. Task-specific fields are optional and validated per task. Every field below is required unless marked, and a missing required field fails the loader rather than defaulting quietly.

FieldTypePurpose
example_idstringStable hash of source document identifier plus sentence index. Regenerating the dataset gives the same ids.
taskenumfls, absa, or factop.
targetstringThe sentence being classified. Never truncated.
context_beforestringPreceding sentences from the same document, in order.
context_afterstringFollowing sentences from the same document, in order.
aspectstring?Required for absa, absent otherwise.
labelstringThe adjudicated label, from the task's label set.
label_sourceenumpublic, human, or llm. This is the track. It is never dropped.
annotator_labelslist?Every individual annotator's label, kept even after adjudication.
codebook_versionstringWhich definition this label was made under.
source_datasetstringName of the originating corpus or collection run.
source_licencestringLicence of the source text. Unknown is not an acceptable value.
doc_idstringDocument identifier, used for leakage checks and for grouped splitting.
doc_typeenumfiling, transcript_prepared, transcript_qa, news, social. Drives per-source reporting.
sentence_indexintPosition in the document.
splitenumtrain, val, or test. Test is gold only.
original_labelstring?For public sources, the label before mapping to this codebook. Kept so the mapping stays auditable.

Splitting rules

  • Group by document. All sentences from one document land in the same split. Sentence-level random splitting leaks context and inflates scores.
  • Test is gold only. Nothing from Track A or Track C ever enters the test split.
  • Validation comes from the same tracks as training. Otherwise validation stops predicting test behaviour.
  • Near-duplicate check across splits after splitting, not before. Boilerplate that repeats across documents is the main offender.

Storage

  • JSONL on disk, one file per task and split. Readable, diffable, and easy to inspect by hand.
  • Parquet for anything large enough that JSONL hurts.
  • Every processed file is accompanied by a .sha256 and a small stats file recording row count and class distribution.
  • Raw data is never edited in place. Transformations produce new files.
  • Large raw files stay out of git. The manifest of what to fetch goes in.

From row to tensor

Input construction

Decided

The one place where the three tasks differ meaningfully. It is deterministic, it is tested, and the exact string that reaches the tokenizer is recoverable from the row plus the config.

Format

The target sentence is marked so the model can find it inside the window. Marker tokens are added to the tokenizer as special tokens so they never get split.

# fls and factop
[CLS] {context_before} [TGT] {target} [/TGT] {context_after} [SEP]

# absa
[CLS] {aspect} [SEP] {context_before} [TGT] {target} [/TGT] {context_after} [SEP]

Putting the aspect in a separate first segment follows the standard sentence-pair setup for aspect classification, and it lets the same sentence appear several times with different aspects and different labels.

Truncation rules

  • The target is never truncated. If a target sentence alone exceeds the budget, the example is dropped and counted, and the count is reported.
  • The aspect is never truncated.
  • Context is trimmed from the outside in, dropping whole sentences, alternating between before and after, until the example fits.
  • Sentences are dropped whole. Never a partial sentence, because a half sentence changes the meaning.
  • Context is capped by sentence count as well as by tokens, so the window is roughly consistent across documents.

Context window, and the ablation that justifies it

Default is two sentences before and two after, capped at 512 tokens total. That default is a guess until it is measured. The first real experiment on each task is a context sweep, because it is cheap and it settles a question that affects everything after.

SettingWhat it testsExpected
0 + 0Target sentence alone. The baseline everyone else publishes.Strong on FLS, weaker on factop
1 + 1Minimal disambiguation.Most of the gain, if there is one
2 + 2The proposed default.Small gain over 1+1
4 + 4Does more context keep helping, or start diluting?Flat or worse, and slower

Whichever wins on validation becomes the config for that task. If 0 + 0 wins, that is a real and publishable finding, and the context machinery stays in the code as an option rather than being deleted.

The encoder

Model and training

Assumed, cheap to change

Primary: ModernBERT-base

Roughly 150M parameters, modern training recipe, long native context that this project deliberately does not use. It is also the natural continuation of the previous work, which makes the comparison to it meaningful.

  • Classification head on the pooled representation, one head per model.
  • Marker tokens added to the vocabulary and their embeddings trained.
  • Max length 512, well under what the architecture supports.

Control: DeBERTa-v3-base

Run once per task with everything else identical. It answers the question the last project could not: how much of the result is the architecture and how much is the data and protocol.

  • Same input builder, same splits, same seeds, same harness.
  • Also the fallback if ModernBERT training proves unstable on Turing hardware.

A real hardware risk worth checking early

The T4 is a Turing GPU. It does not support bf16, and it does not support the newer flash attention kernels that recent encoders assume. ModernBERT is trained in bf16 and will need an attention implementation that works without those kernels, running in fp16 or fp32. Mixed-precision fp16 on a model trained in bf16 sometimes produces overflow and loss divergence.

Mitigation, in order. First, a short smoke run in Slice 1 that trains a few hundred steps and watches for NaN. If fp16 is unstable, try fp32 with a smaller batch and more accumulation. If that is too slow to be workable, switch the primary model to DeBERTa-v3-base and report the reason. This check happens in the first slice, before any real training, because discovering it late would cost the whole phase.

Training configuration

SettingDefaultReasoning
AdaptationLoRA, rank 16, on attention and feed-forward projectionsFits T4 memory comfortably, and the previous project found LoRA beat the full fine-tune it tested. A full fine-tune is run once per task as a comparison, not as the default.
Precisionfp16 with loss scalingThe only mixed precision the T4 supports. Watched for divergence, with fp32 as the fallback.
Max length512Fixed by the product spec. Not a tuning knob.
Batch size16, accumulated to an effective 32Fits 16GB at 512 tokens with room to spare. Accumulation makes the effective size independent of the GPU that happens to be allocated.
Learning rate2e-4 for LoRA, 2e-5 for full fine-tuneStandard starting points. Tuned per task on validation data, and the sweep is recorded.
Epochs3 to 5, early stoppedSmall datasets overfit fast. Selection is by validation macro-F1, not by epoch count.
Evaluation frequencySeveral times per epochThe previous project found frequent macro-F1 checkpoint selection helped. The peak is often mid-epoch.
LossCross-entropy, unweighted by defaultClass weighting is a tuned knob, and the unweighted run is always reported next to any weighted one. Inverse-frequency weighting overcorrected last time and is not the default.
SeedsThree per reported configurationOne seed cannot distinguish a real gain from noise at these dataset sizes.
CheckpointingEvery evaluation, to mounted DriveFree Colab sessions die. A run must resume, not restart.

On focal loss and class weighting. Forward-looking is naturally imbalanced, and the temptation is to reach for a fancier loss immediately. Do not. Run the plain baseline first, then try weighting as a single-variable experiment, and report both. The last project got a result it liked internally from focal loss and then regressed externally, which is exactly the pattern this ordering catches.

Living inside the free tier

T4 budget

Hard constraint

Memory

16GB. A base-size encoder at 512 tokens with LoRA and batch 16 fits with headroom. The headroom is deliberate, because a run that dies at 95% costs a session.

Session life

Sessions drop without warning. Every run checkpoints to Drive and resumes from the last checkpoint, including the optimiser state and the registry row.

Wall clock

Datasets here are thousands of rows, not millions. A run should be tens of minutes. If a configuration needs hours, it is the wrong configuration for this project.

Rules that follow from the constraint

  • Every run is resumable. Not an optimisation, a requirement. Tested by killing a run halfway and restarting it in CI-like conditions at least once per phase.
  • No run depends on a specific GPU allocation. Effective batch size is fixed through accumulation, so a smaller card changes speed and not results.
  • Data preparation happens off the GPU and its outputs are cached, so a lost session never repeats it.
  • The registry row is written at run start, not at the end, so a session that dies still leaves evidence that a run was attempted.
  • Sweeps are sequential and small. No parallel hyperparameter search. Three or four configurations, chosen by reasoning, beats a grid you cannot afford.

The one gatekeeper

Evaluation harness

Refuses bad input

One entry point scores everything: the fine-tuned models, the classical baselines, the LLM baselines, and any public encoder being compared. Anything that produces labels can be scored, and nothing gets scored any other way.

What it enforces

  • Gold hash check. The test file's hash must match the one in the config. A mismatch aborts with an error, not a warning.
  • Split check. Refuses to score a model against any split it was trained on, by comparing example ids.
  • Complete predictions. Every test row must get a prediction. Missing or unparseable outputs are counted as errors and reported, never silently dropped.
  • Registry write. Scoring writes a row. There is no way to get a number out of the harness without leaving a trace.

What it reports

  • Macro-F1, the primary metric, with a bootstrap 95% confidence interval.
  • Per-class precision, recall and F1, and the full confusion matrix.
  • Accuracy, for readers who expect it, clearly marked as secondary.
  • Per-document-type breakdown, so a model that only works on filings gets caught.
  • Calibration: expected calibration error and a reliability curve. Reported, never claimed.
  • Cost and latency, measured on the same run that produced the predictions.
  • The human agreement ceiling, printed in the same table as the scores.

The report card

One JSON file plus one rendered table per evaluation, keyed by run id. The model card and the write-up are generated from these files, so a number cannot appear in a document without existing in a report card first.

{
  "run_id": "fls-a3f21c-20260901T1412",
  "task": "fls",
  "gold_hash": "sha256:7c1e...",
  "n_test": 1000,
  "macro_f1": {"value": 0.000, "ci95": [0.000, 0.000], "method": "bootstrap-10000"},
  "per_class": {"forward_looking": {...}, "not_forward_looking": {...}},
  "by_doc_type": {"filing": {...}, "transcript_qa": {...}},
  "calibration": {"ece": 0.000, "n_bins": 15},
  "cost": {"usd_per_1k_sentences": 0.000, "priced_on": "YYYY-MM-DD"},
  "latency": {"p50_ms": 0.0, "batch32_throughput_per_s": 0.0, "device": "T4"},
  "human_ceiling": {"metric": "cohens_kappa", "value": 0.00, "n_double": 300},
  "evidence_grade": "supported"
}

Zeros are placeholders. The schema is fixed now so that later results cannot reshape what gets reported.

Bootstrap intervals, not just point estimates. With a 1,000-example test set, differences of a point or two are inside the noise. Publishing a point estimate alone invites exactly the kind of overclaiming the last project had to walk back. Every comparison in every document shows the interval.

Competitors, run properly

Baseline runners

Same interface as a model

Every baseline implements the same tiny interface: take a list of examples, return a list of predicted labels with probabilities where available. The harness cannot tell the difference, which is the point.

LLM runner

  • Prompt template committed to the repo and hashed into the registry row.
  • Few-shot examples drawn from the training split, with their ids recorded.
  • Temperature 0, structured output so parsing is reliable.
  • Token counts captured per call, and the total goes straight into the cost figure.
  • Responses cached on disk by hash of prompt plus model, so a rerun costs nothing.
  • Three repeats, with the spread reported.

Classical runner

  • TF-IDF over word and character n-grams, then logistic regression.
  • Hyperparameters tuned on validation, and the search recorded.
  • Also used as a diagnostic: the top weighted features tell you how lexical the task is.
  • Fast enough to rerun on every data change, which makes it a useful canary for data bugs.

How anyone else uses it

Inference and serving

Research release

The library surface

A small Python interface that hides the input construction, because a user who builds the marker string by hand will build it slightly wrong and get worse results than the published numbers.

from triad import Triad

t = Triad.load(["fls", "absa", "factop"])

t.fls(target=s, context_before=b, context_after=a)
t.absa(target=s, aspect="gross margin", context_before=b, context_after=a)
t.factop(target=s, context_before=b, context_after=a)

t.all(target=s, aspect="gross margin", ...)   # one call, three results
  • Models load lazily, so using one does not pay for three.
  • Batch methods for volume work.
  • The same code path the evaluation harness uses. No second implementation to drift.

The demo

  • A Hugging Face Space. Paste a paragraph, pick an aspect, see all three outputs with probabilities.
  • Shows the context window that was actually used, so the behaviour is visible rather than magic.
  • Carries the same limitations text as the model cards, on the page and not behind a link.
  • CPU inference is fine at demo volume, which keeps it free to host.
Not built: a hosted API, batching service, quantised or ONNX exports. All possible later, none part of this project.

Making the claims checkable

Reproducibility machinery

The core of the design

Config resolution and hashing

  • YAML configs with inheritance from base.yaml. Every experiment is a file, and files are diffable.
  • The config is fully resolved before the run, and the resolved version is hashed and stored, so inherited defaults cannot change a run's meaning invisibly.
  • Command-line overrides are allowed and are folded into the resolved config before hashing.
  • The resolved config is written next to the checkpoint.

The registry

  • Append-only JSONL at runs/registry.jsonl. Committed to git, so history is visible.
  • Written at run start, updated at run end. A crashed run leaves a partial row, which is exactly the record you want.
  • Field list is in Program design.
  • A small query tool prints the experiment tree, so the history of what was tried stays readable.

Determinism, and its limits

  • Seeds are set for Python, NumPy and Torch, and recorded.
  • Data ordering is seeded and deterministic.
  • Full bitwise determinism on GPU is not promised, because forcing it is slow and fragile. Instead, three seeds are run and the spread is published, which is more honest and more useful.
  • Library versions are pinned in a lock file and captured in every registry row.

What runs before anything merges

Testing and CI

Blocking

CI has no GPU, so it tests everything except real training. The data invariant checks matter most, because those are the failures that silently invalidate results.

Data invariants

  • No example id appears in two splits.
  • No document id spans splits.
  • Near-duplicate similarity across splits stays below a fixed threshold.
  • Every row has a non-empty label_source, source_licence and codebook_version.
  • The test split contains only label_source == "human".
  • Every label is inside the task's declared label set.
  • Class distribution matches the recorded stats file, so silent data changes get caught.
  • Recorded file hashes match the files on disk.

Code tests

  • Input construction, including every truncation edge case. A long target, an empty context, an aspect containing marker-like text.
  • Metric functions against hand-computed values on tiny fixtures.
  • Bootstrap intervals against a known case.
  • Registry writing and reading, including the crashed-run partial row.
  • Config resolution and hash stability, so the same config always hashes the same.
  • A CPU smoke train: two steps on ten fake examples, proving the loop runs end to end.
  • The harness refuses a wrong gold hash. This test is the safety net for the project's main failure mode, so it is written first.

Getting it out

Release pipeline

Generated, not typed

Cards are generated from report cards and registry rows. Nobody types a number into a Markdown file, because that is where numbers go stale and drift apart between documents.

1

Freeze the candidate

Pick the winning run from validation results. Record why it won.

2

Run the single test evaluation

Once. Writes the report card and the registry row.

3

Generate the model card

Template plus report card plus codebook. Includes limitations and the human ceiling automatically.

4

Upload the dataset

Gold set with per-annotator labels, dataset card, codebook version, and licence per source.

5

Upload the weights

Checkpoint, resolved config, and the tokenizer including the marker tokens.

6

Verify from clean

Fresh environment, download the public artifacts, reproduce the table. This is Gate 5 and it can fail the release.

And what was rejected

Choices and rejections

Reference
DecisionChosenRejected, and why
Model shape Three separate encoders A shared trunk with three heads. Gains become impossible to attribute, and every release couples to the other two tasks.
Aspect handling Aspect as a first segment in a sentence pair Injecting markers around the aspect inside the text. It fails when the aspect is implied rather than literally present, and the previous project's entity formatting work did not produce entity reasoning.
Context Neighbouring sentences, 512 tokens Whole documents. Directly tried before, did not work, and the data behind it broke.
Adaptation LoRA by default Full fine-tuning by default. It is heavier on a T4, and the previous evidence favoured LoRA. Full fine-tuning is still run once per task as a comparison.
Experiment tracking A JSONL file in git A hosted tracking service. Another account, another dependency, and the history stops being visible in the repo. A file diffs, survives, and needs no login.
Config format YAML with inheritance Command-line arguments only. Runs stop being reconstructable from the repo alone.
Test set Human gold only, frozen and hashed Public test splits as the headline. Their label definitions differ from the codebook, which makes the headline number mean something slightly different from what it says.
Primary metric Macro-F1 Accuracy. On an imbalanced task like forward-looking it rewards ignoring the class you care about.
Serving A library plus a demo Space A hosted API. Out of scope for a research release, and it creates an obligation nobody signed up for.
