One pipeline, three models, no path around the protocol

The technical design. A shared harness that all three tasks run through unchanged, a data schema that makes provenance impossible to lose, and a training setup that reaches 8,192 tokens on the cheapest hardware that will carry it. Where a choice is forced by the hardware, that is said out loud, and long context is where the hardware pushes back hardest.

Constraint

Two things shape every decision here. A 16GB GPU with a session that can vanish, and an 8,192-token input that does not fit that GPU comfortably. Where the two conflict, the section says which one gave way.

How the pieces fit

System shape

Shared across all three tasks

One pipeline, parameterised by task. The task defines its label set, its input builder and its data sources. Everything downstream of that is identical code, which is what makes the three results comparable to each other.

1. IngestRaw documents in, passages and sentences out. Structure preserved, sentence splitting, deduplication, document and position recorded on every row.
↓
2. LabelFour tracks. Public sets are mapped to the codebook. The reference test set is labelled once by one pinned frontier model and cached. The referee set is borrowed whole from published human-labelled datasets, then matched back into its source documents so the passage can be rebuilt. Training labels go through k cheap routed models and a label model. Each writes its own provenance.
↓
3. Split and freezeThe borrowed set becomes test plus development and is hashed, along with its reconstructed passages. Training and validation splits come from the other tracks. Leakage checks run here and can fail the build, including the check that no borrowed row leaked into training.
↓
4. Build inputsPassage assembled around the target span, aspect injected for ABSA, trimmed to the configured length by a rule that never cuts the target. Truncation rate measured and asserted here.
↓
5. TrainConfig-driven fine-tune at each rung of the length ladder, as a serverless GPU job. Writes a registry row, checkpoints to a persistent volume, records its own dollar cost.
↓
6. EvaluateSame harness for the model and every baseline. Checks the test-set hash before it will score anything. Emits one report card.
↓
7. ReleaseWeights, dataset and model card to Hugging Face, with numbers copied from the registry rather than retyped.

One row, everything you need to trust it

Data schema

Provenance enforced

Splitting rules

  • Group by document where a document identifier exists. All sentences from one document land in the same split. Sentence-level random splitting leaks context and inflates scores. For FiQA the grouping key is the target company, because there is no document.
  • Two test splits, kept apart. The reference split carries the headline and the referee split carries the match-or-exceed claim. Nothing from Track A or Track C ever enters either one.
  • The reference never votes in Track C. The harness fails the build if the pinned reference identifier appears in the labelling-function model list. A model may teach or it may grade, never both.
  • The reference appears only on test rows. A reference label on a row whose split is train or val, or on a development row, fails the build. That check is what keeps Gate 4 tuning honest.
  • A borrowed row is banned everywhere else. These datasets ship train splits that look like free training data. Any row whose borrowed_row_id appears in test or development is refused in training, and the build fails on an overlap.
  • Grouping is unverifiable on some borrowed sets. Two of the three ship no document identifier, so doc_id is absent and grouped splitting cannot be enforced. Fall back to near-duplicate checking on full text and say so in the model card rather than implying a grouped split that never happened.
  • Validation comes from the same tracks as training. Otherwise validation stops predicting test behaviour.
  • Near-duplicate check across splits after splitting, not before. Boilerplate that repeats across documents is the main offender.

Storage

  • JSONL on disk, one file per task and split. Readable, diffable, and easy to inspect by hand.
  • Parquet for anything large enough that JSONL hurts.
  • Every processed file is accompanied by a .sha256 and a small stats file recording row count and class distribution.
  • Raw data is never edited in place. Transformations produce new files.
  • Large raw files stay out of git. The manifest of what to fetch goes in.

From row to tensor

Input construction

Decided

The one place where the three tasks differ meaningfully. It is deterministic, it is tested, and the exact string that reaches the tokenizer is recoverable from the row plus the config.

Format

The target span is marked inside the passage so the model can find it. Marker tokens are added to the tokenizer as special tokens so they never get split. The passage is otherwise left as it appeared in the document, speaker tags and all.

# fls and factop
[CLS] {passage[:start]} [TGT] {target} [/TGT] {passage[end:]} [SEP]

# absa
[CLS] {aspect} [SEP] {passage[:start]} [TGT] {target} [/TGT] {passage[end:]} [SEP]

Putting the aspect in a separate first segment follows the standard sentence-pair setup for aspect classification, and it lets the same sentence appear several times with different aspects and different labels. At long lengths the aspect segment is a rounding error, so it stays where it is.

Trimming rules

  • The target is never trimmed. If a target alone exceeds the budget, the example is dropped, counted, and the count is reported.
  • The aspect is never trimmed.
  • The passage is trimmed from the outside in, dropping whole sentences, alternating between before and after, until the example fits.
  • Sentences are dropped whole. Never a partial sentence, because a half sentence changes the meaning.
  • Every drop is recorded on the row. How many tokens went, and from which side. This is what the truncation gate reads.
  • Passages are cut at natural boundaries in ingest, not by a sliding token window. A passage that ends mid-argument is a data bug.

How the passage is assembled matters more than the length. The previous project's long-context failure was here, not in the model. Rows arrived already malformed and more than half were still being cut at 6,144 tokens. Passage assembly gets its own test suite and its own reported statistics, and it is built before any long training run.

The core experiment

Length budget

Decided

Length is the one hyperparameter that gets a full three-seed sweep on every task. It is the project's headline claim and it is also the most expensive knob, so it is measured properly once and then pinned.

LengthCovers roughlyWhat it is there for
512Target plus a few neighboursThe internal control. Every long-context claim is a difference against this run, with everything else identical.
2,048A paragraph block, or a full question and answerTests whether the gain arrives early and then flattens, which is the cheapest good outcome.
8,192An MD&A subsection, a long exchangeThe native ceiling. Tests whether the far tail of the passage carries anything.

Three seeds per rung, per task. Reported on the whole test set and on both halves of the context-sensitivity split, where passages could be rebuilt. Where they could not, the ladder reports cost and agreement with the ensemble instead. The shipped length is chosen on validation and the losing rungs stay in the published table.

The truncation gate

A build-time assertion, not a report. It runs over every split before training and writes its numbers into the registry row.

  • Share of rows losing any passage content at this length. Must be under 5%.
  • Share of rows losing content within two sentences of the target. Must be zero.
  • Rows dropped for an over-long target, counted and listed.
  • Full token-length distribution, with the median and the 95th percentile.
If it fails: the run does not start. Fix passage assembly, or lower the rung and record why. Training through a failed truncation check is the exact mistake this project is built to not repeat.

What the ladder can conclude

  • Long wins on the far half only. The expected result. Ship long, and report that the gain is concentrated where the evidence is distant.
  • Long wins everywhere. Check for leakage before believing it. Longer passages share more text across rows, so the near-duplicate check has to pass at the long length too.
  • Long wins nowhere. Ship 512, publish the ladder, and say the task is decidable from the sentence. That is a useful result and the write-up gives it real space.
  • Long is worse. Also possible. More tokens is more chance to attend to the wrong thing on a small training set. Report it and say so.

Why the ladder is not just 512 against 8,192. Two points cannot tell you whether the curve saturates. If 2,048 gets almost all of the gain, the shipped model is four times cheaper to run for nearly the same score, and that is worth knowing before committing every downstream user to the long configuration.

Buying labels instead of writing them

Weak supervision

Costs real money

The implementation of the programme described in Program design. Three components: a router client that turns models into labelling functions, a label matrix, and a fitted label model that turns votes into probabilities. It reads the same passages the student reads.

The router client

  • One prompt per task, versioned and hashed, shared with the baseline runner so the teacher and the baseline are literally the same code.
  • Sends the assembled passage with the target span marked exactly as the student sees it, at the rung being labelled.
  • Structured output, so a parse failure is rare and is recorded as an abstention rather than a guess.
  • Exact model identifiers pinned in the config, never a floating alias.
  • Every response cached on disk by hash of prompt plus model plus passage. Reruns are free, which at passage length is the difference between a rerun and a second invoice.
  • Token counts and cost captured per call and summed into the run's cost field.
  • A hard spend ceiling in the client itself. It stops, it does not warn.
  • Concurrency with retries and backoff, since a labelling run is tens of thousands of long calls.

Labelling functions

Every function has the same signature: take an example, return a class or abstain. A routed model and a regular expression are the same kind of object here.

@lf(name="fls_modal_future")
def modal_future(ex) -> int | ABSTAIN:
    ...

@lf(name="router:<pinned-model-id>")
def routed(ex) -> int | ABSTAIN:
    ...
  • Heuristic functions read the target span and its immediate neighbours, not the whole passage. They are pure, fast, and unit-tested.
  • Model functions are cached, so they are effectively pure too after the first run.
  • The set of functions and the passage length are both part of the config hash. Changing either makes a new experiment.

Labels are bought per rung

A label produced by a model that read 512 tokens is not a valid training label for a student that reads 8,192. The teacher saw less evidence than the student will, so the student learns to imitate a handicapped teacher, and the length ladder measures nothing.

So the labelling run is repeated at each rung, and the cache key includes the passage, which makes that automatic rather than a discipline. This is the single largest cost consequence of the long-context decision, and it is why the pilot runs before every rung rather than once at the start.

Label matrix and diagnostics

A matrix of examples by functions, with abstentions marked. Before any label model is fitted, the diagnostics are computed on the human development set and written to the registry.

StatisticWhat it tells you
CoverageFraction of rows where the function answers. A heuristic at 15% is fine. A routed model below 90% means the prompt, the parser or the context limit is broken.
Empirical accuracyAccuracy on the development set, where the function answers. The single most useful number for deciding whether a function is worth its cost.
Accuracy on the far halfThe same number restricted to rows whose evidence is distant. A model that only wins on near evidence is not paying for its long passage, and neither is the student it teaches.
Overlap and conflictHow often functions answer the same rows, and how often they disagree. Zero conflict is a warning sign, not a good result.
Pairwise conditional agreementHow often two functions are wrong in the same way on the same row. The direct measurement of the independence assumption, and it is published.
Cost per function per rungDollars per thousand rows at each length. Read next to empirical accuracy, this decides which models stay in the set.

Fitting the label model

  • Snorkel's label model, fitted on the full label matrix without gold labels.
  • Class balance supplied from the development set rather than assumed uniform.
  • Its output is a probability per class, not a hard label.
  • Plain majority vote is fitted and scored alongside, every time. Whichever wins on the development set is used, and both numbers go in the report card.
  • The fitted model is saved and versioned, because refitting it changes every training label downstream.

Training on soft labels

  • Noise-aware loss: cross-entropy against the probability vector, not against an argmax.
  • A confidence threshold drops rows the label model is unsure about. The threshold is chosen on validation data and is a single tunable variable in its own experiment.
  • The hard-label variant is run once as a comparison, because soft labels are an assumption worth testing rather than an article of faith.
  • Rows dropped by the threshold are counted and reported, so nobody discovers later that half the data silently vanished.

The pilot rule, in code. The labelling runner refuses to process more than 500 rows at a given length unless the config names a completed pilot at that length and its measured cost per row. This makes the budget discipline a property of the tool rather than a habit, which matters more here than anywhere else in the project.

The encoders

Backbone bench and training

Bench decides it

The families do not share a ceiling. Comparing a model at 8,192 against one that stopped at 512 measures the ceiling, not the model, and this project already bans that kind of cross-protocol comparison everywhere else.

A report card never carries a delta between two different maximum lengths. The harness refuses to compute one.

How the bench runs

  • One task only, forward-looking, in Slice 1. The other two inherit the answer.
  • 512 tokens, LoRA, three seeds, one shared set of training labels. Nothing else moves.
  • Twenty-seven short runs. At 512 that is a small fraction of the cost of one full ladder, which is why this is affordable at all.
  • Decided on validation macro-F1. The borrowed test set is not opened for it.
  • Every candidate stays in the published table, including the ones that lost.

What the winner buys

  • The best 8,192-capable model climbs the full length ladder. That is the shipped model.
  • If a model that cannot reach 8,192 wins the 512 bench outright, that is reported as its own finding, and the ladder still runs on the best long-capable model. Two claims, kept apart.
  • DeBERTa-v3-base doubles as the architecture control it always was, now without a separate run.
  • Ettin's size sweep gives a parameters-versus-score curve for free, which is the cheapest way to find out whether the medium tier is already at the ceiling.

Where the code has to change

  • Ettin loads through the ModernBERT classes, so it is a config change and nothing more.
  • NeoBERT needs trust_remote_code, a pinned revision, and its own LoRA target-module list. Pinning the revision is not optional when the modelling code lives in the repository.
  • DeBERTa-v3 needs its own pooling path and cannot take the 2,048 config at all. The harness rejects that combination rather than silently truncating.
  • Marker tokens are added to each tokenizer separately, and the added-token count goes in the registry row. Four tokenizers means four chances to get this wrong.

Paying for the GPU is what makes long context possible

On a free T4 this was the plan's largest open risk. The T4 is a Turing card with no bf16 and no support for the flash-attention kernels recent encoders assume. ModernBERT and Ettin were both trained in bf16 and lean on those kernels for both the unpadding path and the memory profile. Without them it falls back to a slower, hungrier path, and long context makes that cost land hardest exactly at the rung the project cares about. 8,192 tokens on a free T4 was genuinely uncertain.

Renting Ampere-class hardware or newer removes the question. bf16 is native, the fast kernels are available, and the full ladder is trainable without contortions. The length ladder stops being a hardware gamble and goes back to being a research question, which is what it was supposed to be.

The smoke check still runs at every rung in Slice 1. It now measures memory, throughput and cost per rung so the ladder can be priced, rather than deciding whether the ladder is possible at all.

What is still not a mitigation. Quietly lowering the length and continuing to describe the model as long-context.

Paid, and billed by the second

Compute platform

Costs tracked per run

Serverless GPU jobs. A training run is a containerised function invoked from the command line, billed only while it executes. Nothing idles, nothing times out mid-run, and there is no notebook session to lose. The length ladder is what this buys.

Why serverless

These jobs are bursty and vary hugely in length. A 512-token run is minutes; an 8,192-token run is longer but still not hours. Paying per second matches that shape. A box rented by the hour would bill through every gap while you read results, and a free session would drop the long rungs halfway.

Hardware class

One Ampere-class or newer GPU with at least 24GB. Native bf16, fast attention kernels, and enough memory to train at 8,192 without fighting for every megabyte. The GPU class is recorded per run, because a length comparison across different cards is not a length comparison.

What it replaces

No mounted Drive, no session keep-alive, no rerunning a lost epoch, and no rung that cannot be attempted. Checkpoints go to a persistent volume, artifacts are pulled down by run id, and the whole thing is scriptable, which is what makes it reproducible.

How a run works

1

Image is pinned

One container image with pinned library versions, built once and reused. The image digest goes into the registry row.

2

Data is mounted, not baked

Processed splits live on a volume, keyed by dataset hash. Rebuilding the image never invalidates the data, which matters when tokenized passages at 8,192 are expensive to rebuild.

3

Job runs and self-reports

Registry row written at start with the config hash and the rung. Metrics, wall time, peak memory, GPU class and dollar cost written at the end.

4

Artifacts pulled by run id

Checkpoint, resolved config and report card come back to the local repo, so the release path is unchanged.

Cost accounting

  • Every registry row carries a dollar cost. GPU seconds times the rate in effect, or router tokens times their rates, recorded with the date.
  • Labelling and training costs are tracked separately, per rung, because they behave differently. Labelling scales with rows and passage length, training scales with sweeps.
  • A running project total is printed by the registry query tool, so the spend is visible without adding up invoices.
  • The write-up publishes the total. "This cost roughly X to build, and here is how it split" is one of the more useful things a reader can take from an open project.

Rules that follow

  • Every run is resumable. A job can still be preempted, and a resumed run is cheaper than a restarted one in money as well as time.
  • Effective batch size is fixed across rungs. Only per-device batch and accumulation move, so a length comparison is a length comparison.
  • GPU class is pinned per experiment and recorded. Comparing rungs across different cards is protocol drift.
  • Data preparation happens off the GPU and its outputs are cached. Passage building and tokenizing at 8,192 is slow enough that this matters.
  • The registry row is written at run start, so a job that dies still leaves evidence it was attempted, and its partial spend is still counted.
  • Sweeps are sequential and small. The length ladder is the sweep. There is no budget for a grid on top of it, and now that is a budget in dollars, not just hours.

Portability is deliberate. The training entry point is a plain function with a config path. The serverless wrapper is thin and lives in src/triad/remote/. Anyone reproducing this on their own GPU runs the same function directly, with no account and no platform, which is what keeps the release genuinely reproducible rather than reproducible-if-you-sign-up.

The one gatekeeper

Evaluation harness

Refuses bad input

One entry point scores everything: the fine-tuned models, the classical baselines, the LLM baselines, and any public encoder being compared. Anything that produces labels can be scored, and nothing gets scored any other way.

What it enforces

  • Test hash check. The test file's hash must match the one in the config, and so must the hash of its reconstructed passages. A mismatch aborts with an error, not a warning.
  • Borrowed-row check. No example id in the test or development set may appear in any training source. This is the specific way a borrowed benchmark gets ruined, because these datasets ship train splits that look like free data.
  • Development set separation. Refuses to score against the test split if the run's development hash overlaps it, which is what stops label-model tuning leaking into the benchmark.
  • Split check. Refuses to score a model against any split it was trained on, by comparing example ids.
  • Complete predictions. Every test row must get a prediction. Missing or unparseable outputs are counted as errors and reported, never silently dropped.
  • Registry write. Scoring writes a row. There is no way to get a number out of the harness without leaving a trace.

What it reports

  • Macro-F1, the primary metric, with a bootstrap 95% confidence interval.
  • Paired difference against a named comparator, bootstrapped over the same examples. This, not two separate intervals, is what settles whether the student matched the ensemble and whether 8,192 beat 512.
  • Per-class precision, recall and F1, and the full confusion matrix.
  • Accuracy, for readers who expect it, clearly marked as secondary.
  • Per-document-type breakdown, so a model that only works on filings gets caught.
  • The long-evidence split, scored separately on the near and far halves. This is where a long-context gain has to appear if it is real.
  • Truncation statistics for the evaluated configuration, so a score is never read without knowing what the model was allowed to see.
  • Calibration: expected calibration error and a reliability curve. Reported, never claimed.
  • Cost and latency, measured on the same run that produced the predictions, on GPU and on CPU.
  • Spend, split into labelling, training and evaluation, for the configuration being reported.
  • The human agreement ceiling, printed in the same table as the scores.

Paired bootstrap, not two intervals side by side. With a 1,000-example test set split into near and far halves, each model's own interval spans several points, and two overlapping intervals say almost nothing about which model is better. Scoring both on the same examples and bootstrapping the per-example difference cancels the shared difficulty of those examples and resolves much smaller gaps. Both comparisons this project lives on are paired: the student against the ensemble, and 8,192 against the 512 control on the far half. The report card has a field for each, so neither can be quietly skipped.

Competitors, run properly

Baseline runners

Same interface as a model

Every baseline implements the same tiny interface: take a list of examples, return a list of predicted labels with probabilities where available. The harness cannot tell the difference, which is the point.

Router and ensemble runner

The same client that produces training labels, pointed at the test set. Sharing the code is deliberate: the teacher and the baseline must be the same thing, or the comparison is between two subtly different systems.

  • Scores each pinned model separately, and the label-model ensemble as one more competitor.
  • Prompt template committed to the repo and hashed into the registry row.
  • The LLM gets the full passage, the same string the encoder was given at its shipped length, with the same target markers. Handing it less would manufacture a win.
  • Few-shot examples drawn from the training split, with their ids recorded.
  • Temperature 0, structured output, parse failures counted rather than retried into silence.
  • Token counts captured per call, and the total goes straight into the cost figure. Long passages make this the dominant cost term, which is the point of the comparison.
  • Responses cached on disk by hash of prompt plus model plus passage, so a rerun costs nothing.
  • Three repeats, with the spread reported.

Classical runner

  • TF-IDF over word and character n-grams, then logistic regression.
  • Hyperparameters tuned on validation, and the search recorded.
  • Also used as a diagnostic: the top weighted features tell you how lexical the task is.
  • Fast enough to rerun on every data change, which makes it a useful canary for data bugs.

Where these models actually get run

CPU inference budget

Measured on every candidate

Most people who download a 150M encoder run it on a CPU. A long passage on a CPU is a real cost and nobody has measured it here, so it gets measured rather than assumed. The number is a tie-break for the shipped model, not a gate.

What gets measured

  • One pinned CPU shape, with the vCPU count and the thread count written into the config. A latency figure without a machine attached means nothing.
  • Batch 1 and batch 8, at every rung the candidate supports.
  • p50 and p95 milliseconds per passage, plus throughput.
  • Three export paths: plain PyTorch fp32, ONNX Runtime fp32, and ONNX with dynamic int8 quantisation.
  • Macro-F1 of the exact export, next to its latency. Quantisation moves scores, and an export that was never scored is not a shipped model.

What is already known to bite

  • ModernBERT and Ettin lose the flash-attention kernels on CPU and fall back to a plain path. Their alternating local and global attention still helps at the long rungs, and how much is exactly what this measures.
  • DeBERTa-v3's disentangled attention is slower per token than its parameter count suggests. Small is not the same as fast, and the 44M checkpoint may not win this.
  • NeoBERT's custom modelling code is the least likely to export. If it will not, it keeps its place in the accuracy table and is not offered as the CPU model. That gets written down, not hidden.
  • Cost per passage on CPU sits in the same table as the GPU and router numbers, so the cheap-inference claim is priced on the hardware a reader would actually use.

The tie-break rule. When two backbones land inside each other's confidence interval on validation macro-F1, the faster one on CPU ships. When they do not, accuracy wins and the latency goes in the card as a known cost. Latency never picks the model before the accuracy question is settled, because that is how you end up shipping a fast model that is worse and calling it a trade-off nobody chose.

How anyone else uses it

Inference and serving

Research release

The library surface

A small Python interface that hides the input construction, because a user who builds the marker string by hand will build it slightly wrong and get worse results than the published numbers. Passing a whole passage is the normal path, not an advanced one.

from triad import Triad

t = Triad.load(["fls", "absa", "factop"])

t.fls(passage=p, target_span=(start, end))
t.absa(passage=p, target_span=(start, end), aspect="gross margin")
t.factop(passage=p, target_span=(start, end))

t.all(passage=p, target_span=(start, end), aspect="gross margin")

# convenience form: the passage is assembled for you
t.fls(target=s, context_before=b, context_after=a)

# whole document: split into passages, then classify every sentence
t.scan(document=doc, tasks=["fls", "factop"])
  • Models load lazily, so using one does not pay for three.
  • Batch methods for volume work, with the batch size defaulting to what fits at the model's length.
  • scan splits a document into passages and classifies every sentence in each. It is one forward pass per target, because the target markers change the input, so a long passage with forty sentences costs forty long passes. That is real and the docs say it plainly rather than implying reuse.
  • A warning if the supplied passage exceeds the model's length, naming how much was trimmed. Silent truncation at inference is the same bug as at training time.
  • The same code path the evaluation harness uses. No second implementation to drift.

The demo

  • A Hugging Face Space. Paste a passage, pick a sentence, pick an aspect, see all three outputs with probabilities.
  • Highlights the passage the model actually read, and greys out anything trimmed, so the length behaviour is visible rather than magic.
  • A toggle that reruns the same input through the 512-token control, so a visitor can see for themselves where the extra context changes the answer.
  • Carries the same limitations text as the model cards, on the page and not behind a link.
  • CPU inference is fine at demo volume, which keeps it free to host.
Not built: a hosted API or a batching service. Both possible later, neither part of this project. ONNX and quantised exports are built, because the CPU numbers below cannot be measured without them.

Making the claims checkable

Reproducibility machinery

The core of the design

Config resolution and hashing

  • YAML configs with inheritance from base.yaml. Every experiment is a file, and files are diffable.
  • The config is fully resolved before the run, and the resolved version is hashed and stored, so inherited defaults cannot change a run's meaning invisibly.
  • Command-line overrides are allowed and are folded into the resolved config before hashing.
  • The resolved config is written next to the checkpoint.

The registry

  • Append-only JSONL at runs/registry.jsonl. Committed to git, so history is visible.
  • Written at run start, updated at run end. A crashed run leaves a partial row, which is exactly the record you want.
  • Field list is in Program design.
  • A small query tool prints the experiment tree, so the history of what was tried stays readable.

Determinism, and its limits

  • Seeds are set for Python, NumPy and Torch, and recorded.
  • Data ordering is seeded and deterministic.
  • Full bitwise determinism on GPU is not promised, because forcing it is slow and fragile. Instead, three seeds are run and the spread is published, which is more honest and more useful.
  • Library versions are pinned in a lock file and captured in every registry row.

What runs before anything merges

Testing and CI

Blocking

CI has no GPU, so it tests everything except real training. The data invariant checks matter most, because those are the failures that silently invalidate results.

Data invariants

  • No example id appears in two splits.
  • No document id spans splits.
  • Near-duplicate similarity across splits stays below a fixed threshold, checked on the full passage and not only on the target. Long passages overlap far more easily, and this is the leakage route long context opens up.
  • passage[target_span] equals target exactly, on every row.
  • Truncation statistics at the configured length are within the gate, and the recorded token distribution matches the data on disk.
  • No passage text is shared between two splits. Grouping by document is meant to guarantee this, and the check proves it rather than trusting it.
  • Every row has a non-empty label_source, source_licence and codebook_version.
  • The test split contains only label_source == "human".
  • Every weak row has votes, probabilities, a labelling-function set version and a label model version.
  • No example id appears in both the development set and the test set.
  • The labelling-function set version records a passage length that matches the rung being trained.
  • Every label is inside the task's declared label set.
  • Class distribution matches the recorded stats file, so silent data changes get caught.
  • Recorded file hashes match the files on disk.

Code tests

  • Passage assembly and input construction, including every trimming edge case. A target longer than the budget, a target at the very start or end of the passage, an empty passage, an aspect containing marker-like text, and a passage that is exactly at the limit.
  • The truncation gate itself. A fixture that is deliberately over-length must make the gate fail. This test is written before the gate is used, because a gate that silently passes is worse than no gate.
  • Token accounting: the recorded passage_tokens matches what the tokenizer actually produces, at every rung.
  • Metric functions against hand-computed values on tiny fixtures.
  • Bootstrap intervals against a known case.
  • Registry writing and reading, including the crashed-run partial row.
  • Config resolution and hash stability, so the same config always hashes the same.
  • A CPU smoke train: two steps on ten fake examples, proving the loop runs end to end.
  • The harness refuses a wrong test hash. This test is the safety net for the project's main failure mode, so it is written first.
  • The harness refuses a borrowed row that appears in training. Same reason, new failure mode. A fixture puts one test row into a training file, and the build must fail.
  • The harness refuses a run whose development set overlaps the test set.
  • Label matrix construction, including abstentions and a function that throws.
  • Label model and majority vote against a tiny fixture with known answers.
  • The router client's spend ceiling actually stops the run.
  • The cache returns identical results for identical prompts, so a rerun cannot silently cost money.
  • The labelling runner refuses a full run at a rung with no completed pilot.

Getting it out

Release pipeline

Generated, not typed

Cards are generated from report cards and registry rows. Nobody types a number into a Markdown file, because that is where numbers go stale and drift apart between documents.

1

Freeze the candidate

Pick the winning run from validation results. Record why it won.

2

Run the single test evaluation

Once. Writes the report card and the registry row.

3

Generate the model card

Template plus report card plus codebook. Includes limitations automatically, and the human ceiling where the source published one, or the words "not published by the source" where it did not.

4

Upload the dataset artifact

Not a mirror of somebody else's labels. A link to the borrowed source, our splits as row identifiers, and the reconstruction as document identifiers with character offsets, so anyone can rebuild the exact passages. Plus the dataset card, codebook version, and licence per source.

5

Upload the weights

Checkpoint, resolved config, and the tokenizer including the marker tokens.

6

Verify from clean

Fresh environment, download the public artifacts, reproduce the table. This is Gate 6 and it can fail the release.

And what was rejected

Choices and rejections

Reference
DecisionChosenRejected, and why
Model shape Three separate encoders A shared trunk with three heads. Gains become impossible to attribute, and every release couples to the other two tasks.
Aspect handling Aspect as a first segment in a sentence pair Injecting markers around the aspect inside the text. It fails when the aspect is implied rather than literally present, and the previous project's entity formatting work did not produce entity reasoning.
Context A passage with a marked target span, up to 8,192 tokens A 512-token window of neighbouring sentences. It was the earlier plan, and it hands the LLM baseline a permanent advantage in evidence. It survives as the internal control at the bottom of the length ladder.
Getting past 512 A base model pretrained at 8,192 Position-embedding extension or interpolation on a 512-token model. It needs continued pretraining to work properly, there is no budget for that here, and the result would be impossible to attribute between the extension and the task.
Whole documents Passages cut at natural boundaries Hierarchical models or chunk-and-aggregate over a full 10-K. Two moving parts instead of one, no way to attribute a gain, and 8,192 tokens already covers the passage a human would read.
Passage boundaries Document structure: paragraph, section, question-and-answer turn A fixed sliding token window centred on the target. It is simpler and it cuts arguments in half, which is the failure mode that broke the previous long-context data.
Backbone Four families benched at 512, then the winner climbs the ladder Picking ModernBERT-base on reputation, which is what the earlier plan did. Also rejected: running the full length ladder on all nine candidates, which multiplies the most expensive experiment in the project by nine to answer a question the 512 rung already answers.
Model size Small and medium tiers first, roughly 32M to 250M Starting at 400M or 1B. The accuracy gain is unknown, the CPU cost is not, and Ettin's size sweep makes adding the large tier later a one-config job if the medium tier turns out to be capped.
CPU inference Measured on every candidate, and a tie-break between close backbones Publishing GPU-only numbers, which describe a machine most downloaders do not have. Also rejected: making CPU latency a gate, which would pick the backbone before the accuracy question was settled.
Adaptation LoRA by default Picking one on memory grounds. Paid Ampere-class hardware makes both affordable at every rung, so the previous project's LoRA result gets re-tested rather than inherited.
Training labels k routed models plus heuristics, combined by a label model Hand-labelling tens of thousands of passages, which the schedule cannot absorb. Also rejected: one model sampled k times, because its votes are too correlated for the label model to learn anything from. Also rejected: labelling once at 512 and reusing those labels at every rung, which would make the length ladder meaningless.
Compute Serverless GPU, per-second billing Free Colab, which capped precision, capped memory and made the 8,192 rung a genuine gamble. Also rejected: a GPU rented by the hour, which bills while you read results, and managed cloud training, which is more setup than three small fine-tunes justify.
Experiment tracking A JSONL file in git A hosted tracking service. Another account, another dependency, and the history stops being visible in the repo. A file diffs, survives, and needs no login.
Config format YAML with inheritance Command-line arguments only. Runs stop being reconstructable from the repo alone.
Test set Two frozen hashed splits. A reference split for the fidelity headline, a borrowed human split as the referee Reporting agreement with the reference as if it were accuracy. It is fidelity to one model's opinion. Also: claiming to beat the frontier model on labels that same model wrote, which is arithmetically impossible and would be caught by nobody but the author.
Primary metric Macro-F1 Accuracy. On an imbalanced task like forward-looking it rewards ignoring the class you care about.
Serving A library plus a demo Space A hosted API. Out of scope for a research release, and it creates an obligation nobody signed up for.
