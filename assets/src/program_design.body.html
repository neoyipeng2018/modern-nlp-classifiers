How the work gets run without producing numbers you have to retract

The rules everything else follows from

Operating principles

Enforced in CI

Seven rules. Most of them are enforced by a test or a script, not by discipline. Anything that depends only on remembering will eventually be forgotten.

1

Freeze the test set before training anything

The gold test set for a task is built, hashed and committed before the first training run on that task. Its hash goes in the config. The eval harness refuses to score against a hash it does not recognise.

2

One variable per experiment

A run changes one thing. If two things change, the run tells you nothing about either. Multi-change runs are allowed only as a deliberate "does anything work at all" probe, and they are labelled as such in the registry.

3

Provenance travels with every row

Source, licence, label origin, codebook version. A row without provenance never enters a training set. A data-loading test enforces this.

4

Never look at the test set

Prompt tuning, hyperparameter search, checkpoint selection, threshold picking. All of it happens on validation data. The test set is opened once per model, at the end.

5

Every claim names its refutation

Before writing a claim, say what result would have disproved it. If no such result exists, the sentence is an opinion and gets written as one.

6

Report the human ceiling next to the model

A macro-F1 of 0.84 means one thing if annotators agree 0.95 of the time and something else entirely if they agree 0.86 of the time. The ceiling is always in the table.

7

Negative results ship

A model that misses the bar is released with the miss stated. A method that did not help gets a paragraph in the write-up. The project is worth more as an honest record than as a set of wins.

8

If it is not in the registry, it did not happen

A number without a registry row cannot be quoted anywhere. Not in the README, not in the model card, not in conversation. This is the rule that the last project most needed and did not have.

Sequencing

Phases

One task per phase

Each phase takes one task from raw data to a released model. The first phase also builds the shared machinery, so it is the longest by a wide margin. Detailed scope for each is in Vertical slices.

Phase 1 — Forward-looking, and the harness

First

Goes first because the labels are the simplest to define and public annotated data is the easiest to find. That keeps the risk in the machinery rather than in the task. Everything reusable is built here: data schema, passage builder, eval harness, run registry, baseline runners, model card template, CI.

It also runs the length ladder for the first time, which is the phase's real headline. Whatever 512 against 8,192 says on forward-looking sets the prior for the other two tasks, and it decides whether the long-context claim has legs at all.

Exit: one released model, one released gold set, a published length ladder, and a harness the next two phases use unchanged.

Phase 2 — Aspect-based sentiment

Second

Second because it adds one new thing to a proven pipeline: the aspect goes into the input. Public data exists in the form of aspect-level financial sentiment sets with continuous scores, so there is also a score-to-class mapping to decide and document.

Exit: released model, released gold set, a length ladder for this task, and a documented mapping from any continuous source scores to the three classes.

Phase 3 — Fact versus opinion

Third

Last because the public data is weakest, so this phase leans hardest on your own annotation and on LLM silver labels. Doing it last means the annotation tooling and the silver-label pipeline are already proven on two easier tasks.

Exit: released model, released gold set, a length ladder for this task, and a measured overlap with the forward-looking labels.

Phase 4 — Suite release

Last

The cross-model comparison table, the demo Space, and the write-up that tests the thesis. This is where the three models stop being three projects and become one claim.

Exit: public write-up with every number graded, and a demo anyone can paste text into.

Phases do not overlap. The temptation after Phase 1 is to start all three at once. Do not. The harness will need changes discovered in Phase 2, and changing it while three models are mid-training is how protocol drift starts.

Every task runs its own ladder, and here is the rule for shortening it. The full ladder is three rungs at three seeds. Phases 2 and 3 may drop to the winning rung plus the 512 control, two rungs at three seeds, but only if Phase 1's ladder separated cleanly outside the noise band. If Phase 1 came out flat or mixed, the full ladder runs every time, because a flat result is exactly the case where one task's answer says nothing about another's. Whichever version ran is recorded in the model card.

Where labels come from

Data program

Decided

Three tracks, kept apart at every stage. They have different reliability, different licences and different failure modes. Merging them without a record is the mistake the last project made, and it made the results impossible to reconstruct.

Track A — Public labelled

Reproducible

Existing annotated datasets. Cheap, citable, and other people can check them. The catch is that none of them were labelled under this codebook, so their label meaning is close but not identical.

  • Used for training and validation.
  • Never used as the gold test set.
  • Each source gets a mapping note saying how its labels were translated.

Track B — Gold human

The benchmark

Labelled by you, under the codebook, on text sampled from the real target distribution. This is the only track that decides whether a model passed.

  • Test set only. Never trained on. Never tuned against.
  • Frozen and hashed before training starts.
  • Individual annotator labels kept, not just the adjudicated one.

Track C — Silver LLM

Scale, with doubt

Claude labelling sentences from public filings and transcripts at volume. Fast and cheap, and it inherits whatever the LLM gets wrong, which is exactly what you are trying to beat.

  • Training only, in its own split.
  • A human-reviewed sample measures its accuracy against the gold codebook.
  • Its contribution is proven by an ablation, never assumed.

The circularity problem, stated plainly

The success bar is beating a few-shot LLM. Track C trains the model on that same LLM's labels. Left alone, this makes the headline comparison meaningless, because a student cannot cleanly beat its teacher on the teacher's own answers.

How it is handled. Three things, all required. The gold test set is human-labelled, so the LLM never grades its own homework. Every model is reported twice, once trained without Track C and once with it, so the reader sees the claim both ways. And the headline claim is always stated against the Track A plus B model, with the Track C model reported as a separate result.

Sampling rules for the gold set

  • Sample from the target distribution, not from what is easy. Mix filings, transcript prepared remarks, transcript question-and-answer, and news, in proportions written down before sampling.
  • Stratify by document type so per-source performance can be reported.
  • Do not balance the classes by sampling. The natural rate of forward-looking sentences is part of the problem. Report the rate and handle imbalance in training, not in the test set.
  • Deduplicate before annotating. Boilerplate repeats across filings and will otherwise dominate the set.
  • Keep the document and sentence position for every example, so leakage across splits can be checked later.
  • Keep the whole passage, not the sentence. The gold set stores the passage the annotator read. Storing only the sentence would make the long rungs untestable after the fact, and re-fetching the surroundings later is how provenance broke last time.
  • Sample passages long enough to matter. If every gold passage is 300 tokens, the ladder has nothing to measure. Stratify the sample by passage length so the long rungs are actually exercised, and publish the length distribution.
  • Sample once and freeze. Re-sampling after seeing results is the same as tuning on the test set.

Long passages make the licence problem worse. A single sentence from a paid transcript is arguably a quotation. Two thousand tokens of it is not. Redistribution terms get checked against the passage length actually being published, not against the sentence. Where terms are unclear, publish document identifiers and character offsets instead of the text, and ship a script that rebuilds the passages from the source.

The most valuable and least glamorous work

Annotation program

Open item inside

The gold sets are what make this project citable. They are also the part most likely to be rushed. This section fixes the process so the quality is measurable rather than asserted.

Process

  1. Draft the codebook from the definitions in Product. Version it.
  2. Pilot on 50 examples. Every disagreement or hesitation becomes a new rule in the codebook. Expect the codebook to roughly double in size here.
  3. Re-pilot on 50 fresh examples under the revised codebook. If you are still hesitating on more than one in five, the label definition is wrong, not the annotator.
  4. Bump the codebook version and discard the pilot labels. They were made under a different definition.
  5. Annotate the full 1,000 in sittings of no more than 150. Fatigue shows up as label drift, and drift late in the set is invisible unless you shuffle.
  6. Shuffle before annotating so any drift spreads evenly rather than landing on one document type.
  7. Re-annotate 100 examples from early in the run, blind, at the end. Agreement with your own earlier labels is the drift measurement. Publish it.
  8. Adjudicate disagreements with a written reason, and fold the reason back into the codebook for next time.
One extra field per row: evidence distance. Two clicks, and it is what makes the whole long-context claim testable.

Measuring quality

  • Two annotators is the strong version. 300 examples double-annotated, Cohen's kappa reported per task. Target above 0.7. Below 0.6 means the codebook has to be rewritten before any model is trained.
  • One annotator is the fallback. If no second person is available, self-agreement on a blind re-annotation is the ceiling estimate. It is weaker evidence and must be labelled as such everywhere it appears.
  • An LLM is not a second annotator. Claude's labels can be a useful third opinion for finding examples worth a second look. They cannot be the agreement ceiling, because the LLM is the thing being benchmarked.
  • Publish the disagreements. The examples annotators split on are the most informative part of the dataset. Keep them in, with both labels.
Open decision: is a second human annotator available? This changes how the ceiling is reported in every model card, so answer it before Phase 1 annotation starts.

Recording evidence distance

The annotator answers a second question on every gold row: where was the evidence that decided this label? It takes seconds, it is recorded before any model exists, and it is the only honest way to test whether long context helps.

ValueMeansRole in the results
in_targetThe sentence alone was enough.Long context should change nothing here. If it does, something is wrong.
nearNeeded a sentence or two either side.What a 512-token model can already reach.
farNeeded something further away. A speaker tag, an earlier number, a heading, a prior paragraph.The subset the whole claim rests on.
unknownThe annotator could not say.Reported, excluded from the split, and the rate is published.
  • Record it before seeing any model output. Assigning it afterwards would let the results decide the split, which is the same sin as tuning on test.
  • It is annotator judgement, not ground truth. Say so wherever the split appears. On the double-annotated portion, agreement on this field is measured and published alongside the label agreement.
  • If far comes in under 10% of the gold set, the long-context question is close to untestable on that task. Report that rather than reading a difference out of forty examples.

Time is the real constraint. 1,000 sentences per task at a realistic pace is several sittings of focused work, three times over. Budget it as a first-class task in each phase, not as something squeezed in around training runs. If the budget will not stretch, cut the set to 600 and report the wider confidence intervals honestly. Do not cut the double-annotated portion, because that is what makes the rest of the numbers interpretable.

The thing you have to beat

Baseline program

Same harness as the models

A weak baseline makes a weak result look strong. The LLM baseline gets the same care as the model, or the headline claim is worthless.

BaselineWhy it is runRules
Majority class The floor. If a model is near this, something is broken. Computed from the training split, applied to test.
TF-IDF + logistic regression Tells you how much of the task is surface vocabulary. Forward-looking in particular may be largely lexical, and that is worth knowing and saying. Hyperparameters tuned on validation only.
The same encoder at 512 tokens The internal control for the long-context claim. Same data, same recipe, same seeds, shorter input. Every statement about what long context bought is a difference against this run. Identical in every respect except max length. Run at three seeds, like the long rungs.
Few-shot Claude, small model The realistic cheap alternative a practitioner would reach for instead of your model. Prompt developed against validation data. Few-shot examples drawn from training data. Never from test. Gets the full passage.
Few-shot Claude, large model The quality ceiling of the prompt-only approach. This is usually the number to beat. Same prompt discipline. Temperature 0, and the exact prompt is committed to the repo.
Zero-shot LLM Shows what the prompt engineering was worth, which is itself a useful published result. The codebook definition goes in the prompt, and nothing else.
Existing public finance encoder Shows the delta over what is already downloadable, where a comparable model exists. Label spaces must be mapped explicitly, and the mapping published. Where no clean mapping exists, do not force one.

Fairness rules for the LLM baseline

  • The prompt gets a real effort budget. Several iterations against validation data, not one attempt.
  • The full codebook definition goes in the prompt. Do not handicap the LLM by underspecifying the task.
  • Parsing failures count as errors, and the failure rate is reported separately.
  • The LLM reads the same passage the model reads. Not a trimmed version, not the sentence. If the encoder ships at 8,192 tokens, the LLM gets those 8,192 tokens.
  • Where the source passage is longer than the encoder's limit, both get the same trimmed passage, and the trimming is done once by the same code.
  • Run it three times and report the spread, because even at temperature 0 the output can move.

Measuring the cost claim

  • Count actual input and output tokens for the whole test set. Do not estimate. Long passages make input tokens the dominant term, and that is the heart of the cost story.
  • Price at published list rates, with the date recorded, since prices change.
  • For the encoder, report throughput at its shipped length on a T4 and the cost of that GPU-time, so the comparison is like for like.
  • Report cost per 1,000 passages for both, and the ratio, at every rung of the ladder. A reader choosing 2,048 over 8,192 needs to see what that saves.
  • State the cost of any rented GPU time used for the long rungs. Free-tier training is part of the pitch, and if it stopped being true, say so.
  • State clearly that the encoder needed a labelled dataset and a training run, and the LLM did not. That is a real cost, and hiding it makes the comparison dishonest.

What every run must record

Experiment protocol

Registry-backed

One row per run in a registry file, written by the training script and not by hand. A run without a row cannot be quoted. This is the direct fix for the previous project's reproducibility gap.

Registry row fields

FieldMeaning
run_idStable identifier, generated from the config hash and the start time.
taskOne of fls, absa, factop.
hypothesisOne sentence, written before the run, saying what this run is testing.
variableThe single thing changed relative to the named parent run.
parent_run_idThe run this one is a variation of. Makes the experiment tree readable.
config_hashHash of the full resolved config, including data selection.
data_revisionDataset version and hash for every split used.
gold_hashHash of the frozen test set. Mismatch aborts the run.
max_lengthWhich rung of the length ladder this run is. A first-class field, because it is the project's main variable.
truncationMeasured trimming statistics at this length, written by the gate before training starts. A run whose gate failed has no training metrics and says why.
control_run_idThe 512-token run this one is compared against. Empty on the control itself.
seedRandom seed. Three seeds per reported configuration.
envLibrary versions, GPU type, CUDA version. Says plainly whether this rung ran on free or rented hardware.
metrics_valValidation metrics, per epoch.
metrics_testTest metrics. Empty until the run is promoted to a final evaluation.
artifact_pathWhere the checkpoint actually is.
evidence_gradeSupported, reported, compromised, or not run.
notesAnything that went wrong. Especially anything that went wrong.

Run discipline

  • Write the hypothesis first. If you cannot say what the run tests before starting it, you are not running an experiment, you are hoping.
  • Three seeds before any comparison. A one-seed difference of a point or two is noise. Report mean and spread.
  • Checkpoint selection on validation macro-F1, evaluated often enough to catch the peak. The previous project found frequent selection helped.
  • Test evaluation is a separate deliberate step, run once per candidate model, and it writes to the registry.

When a run is compromised

  • Grade it compromised in the registry with the reason. Do not delete it.
  • Any number from it is unusable, including numbers that look good.
  • If the compromise came from a code path, add a test that would have caught it before rerunning.
  • A preprocessing assertion that stops a run is a success, not a nuisance. The last project had one fire correctly and it saved a bad result from shipping.

Permission to continue

Decision gates

Can fail

Each gate is a real stop. Failing one means fixing the cause, not carrying on and hoping the next phase covers it. A gate that never fails is decoration.

Gate1

Codebook is usable

Two pilot rounds done. Hesitation rate under one in five. Kappa above 0.7 if a second annotator exists, or stable self-agreement if not.

If it fails: rewrite the label definitions. Do not annotate 1,000 examples against a definition you are unsure of. This is the cheapest failure in the whole programme and the most expensive one to skip.
Gate2

Data is clean, and the passages are intact

No near-duplicates across splits, checked on full passages. Every row has provenance. Every target span resolves inside its passage. Licence confirmed for every source that will be redistributed, at the passage length being published. Class rates and token-length distribution recorded.

If it fails: no training run starts. Leakage found later invalidates everything downstream of it, and long passages make leakage easier, not harder.
Gate3

The length budget holds

At the rung about to be trained: trimming affects under 5% of rows, nothing within two sentences of a target is lost, and the configuration actually fits the available hardware for a full run.

If it fails: the run does not start. Fix passage assembly, or drop to a lower rung and record why. This is the gate the previous project did not have, and its absence is the whole reason the earlier long-context result was uninterpretable.
Gate4

Model beats the classical baseline

The fine-tuned encoder clearly beats TF-IDF plus logistic regression on validation data.

If it fails: stop and diagnose. Either the task is lexically trivial, which is a publishable finding on its own, or the training pipeline is broken. Do not tune hyperparameters until you know which.
Gate5

Model meets the success bar

Test macro-F1 at or above the best LLM baseline on the same passages, cost ratio at least 50×, latency within budget at the shipped length, all measured once on the frozen gold set. The full length ladder is reported, including the rungs that lost.

If it fails: the model still ships, with the miss in the model card and an honest section in the write-up about why. Failing this gate does not block the next phase. Hiding it does. A ladder that comes out flat is a reported result, not a failure.
Gate6

Release is reproducible

A clean checkout plus one command reproduces the published table from the released checkpoint and the released dataset.

If it fails: nothing is published. A number that cannot be reproduced from the public artifacts is exactly the problem this whole programme exists to avoid.

The programme-level stop rule. If Phase 1 fails Gate 1 or Gate 2 twice, stop and reconsider the task definition before spending time on Phases 2 and 3. Three models built on a shaky label definition is three times the wasted effort.

And the long-context stop rule. If Gate 3 fails twice at 8,192 on the same task, ship the highest rung that passes and say in the model card that 8,192 was attempted and abandoned, with the reason. Do not keep retrying it, and do not describe the shipped model as long-context if it is not.

Who does what

Roles and working style

Assumed

Only you can do this

  • Annotation. The gold labels are the human contribution, and delegating them to a model destroys their purpose.
  • Codebook judgement calls. Every hard case resolved becomes a rule everything else follows.
  • Deciding what a result means. Especially deciding when a result is not good enough to claim.
  • Licence and redistribution calls.

Good agent work

  • Harness, scripts, tests, CI. Well-specified engineering with a clear definition of done.
  • Dataset surveys. Finding what exists and what its terms are, with links, for you to verify.
  • Baseline runners and the cost measurement plumbing.
  • Silver labelling at volume, once the prompt is fixed.
  • Drafting model cards and the write-up, from registry numbers rather than from memory.

Rule for agent work. An agent may write any code and may draft any text. An agent may not decide that a number is good enough to publish, and may not put a number anywhere without its registry row and evidence grade. Any pull request that adds a number without a registry reference gets rejected.

What will probably go wrong

Risk register

Live
RiskWhy it is likelyResponse
Annotation stalls the project 3,000 careful judgements is genuinely a lot of work, and it is the least fun part. Cut to 600 per task before cutting quality. Keep the double-annotated portion. Report the wider intervals.
Public data does not match the codebook Every existing dataset was labelled for someone else's purpose. Publish the mapping, and report performance on the gold set separately from performance on public test splits. Never blend the two into one headline.
Public data ships sentences without their documents Almost every published sentence-level finance set was built for short-context models. The surrounding text was thrown away. Ask this question during the source survey, not during training. Rows without a recoverable passage are marked and counted. If they dominate the training set, the long rungs train on less real context than the short rung, and that would break the comparison. In that case, say so and lean on gold and silver data where the passage was kept.
Fact versus opinion has no usable public data It is the least studied of the three in a finance setting. Plan for it. Phase 3 is scheduled last precisely so the silver pipeline is proven by then. Accept a smaller training set and say so.
The LLM baseline wins Frontier models are strong at exactly this kind of short classification task. Ship the result. "A 150M encoder gets within a point of a frontier model at one fiftieth the cost" is a good outcome and an honest one.
8,192 tokens does not fit a free T4 The T4 is a Turing card with no bf16 and no flash-attention support, so the memory-efficient path ModernBERT expects is not there. This is the single most likely thing to go wrong. Smoke-checked at every rung in Slice 1, before anything depends on it. Fallbacks in order: batch 1 with accumulation, gradient checkpointing, then rented L4 or A100 time for the long rungs with the rental disclosed in the card.
Long context does not help Small training sets and more tokens to attend to is a real recipe for no gain, or for a loss. The 512 control runs on every task, so the answer is measurable rather than arguable. A flat ladder ships as the short model, with the ladder published. That is a result the field is short of.
Long passages leak across splits Boilerplate repeats across filings. At 8,192 tokens two rows from different documents can share most of their text. Near-duplicate checks run on full passages, not targets, and they fail the build. Grouped splitting by document stays in place on top of that.
The gold set has no long-evidence examples Sampling by sentence tends to pull self-contained sentences, and then there is nothing for the long rungs to win on. Stratify the gold sample by passage length. Record evidence distance at annotation time. If the far bucket lands under 10%, say the question was untestable on that task rather than reading a result out of noise.
Annotation gets slower Reading a 2,000-token passage per label is not the same job as reading a sentence. Budget fewer examples per sitting. Cut the set to 600 before cutting the passage. A label made without reading the context is worse than no label at all now that context is the whole point.
Licences block the dataset release Financial text is commercially valuable and often restricted. Check licences before annotating, not after. Prefer EDGAR, which is public domain in the US. Release document identifiers and offsets rather than raw text where terms are unclear.
Scope creep back into non-goals Aspect extraction, whole-document modelling and hierarchical chunk aggregation all feel like natural next steps once the input is already long. The non-goals list in Product, plus the rule that adding one back needs a decision-log entry. 8,192 is the ceiling and the caller cuts documents into passages.
The thesis turns out to be wrong Three labels may simply not cover as much of finance NLP as claimed. That is a finding. The write-up has a section for what the three labels miss, and it gets written whatever the answer is.

The output that outlives the models

Write-up plan

Phase 4

Written from the registry, not from memory. Every number traceable to a run row. The structure is fixed now so the results cannot quietly reshape the argument later.

Sections

  1. The thesis, stated as a claim that could be wrong.
  2. The three tasks, with the full codebooks.
  3. The protocol, before any results. Deliberately first, so the reader judges the method before seeing the numbers.
  4. Data, including the tracks and their reliability.
  5. Results, one table per task, every baseline, every interval, the human ceiling in the same table.
  6. Does length help, the full ladder on all three tasks, split by evidence distance, with the 512 control alongside. This is the paper's actual contribution and it gets its own section whichever way it comes out.
  7. Cost and latency, per rung, with the training cost and any rented GPU time stated too.
  8. What did not work, at similar length to what did.
  9. Thesis test, taking real finance NLP tasks and showing coverage and gaps.
  10. Limitations and quarantined claims.

Rules for the text

  • No number without an evidence grade.
  • No comparison across different protocols, ever, even with a caveat.
  • Confidence intervals in every results table, not just the text.
  • The word "state of the art" does not appear.
  • Where an earlier plan changed, say so and say why. The move from 512 tokens to 8,192 is the largest such change and it gets its own paragraph, including what the previous project's long-context failure did and did not show.
  • "Long context helps" is never written without the control run, the interval, and the evidence-distance split next to it.
  • The thesis section reports what the three labels miss, in the same detail as what they cover.
